## Redis 缓存穿透、缓存雪崩和缓存击穿分别是什么？如何解决？

**锚点**：`穿透查不存在（布隆+空值）、击穿热点 key 过期（互斥锁+逻辑过期）、雪崩批量过期/宕机（随机 TTL+集群）`

| 问题 | 定义 | 解决 |
|------|------|------|
| 穿透 | 查**不存在**的数据，缓存和 DB 都没有 | 布隆过滤器 + 缓存空值 |
| 击穿 | **热点 key 过期**瞬间大量并发打 DB | 互斥锁 + 逻辑过期 |
| 雪崩 | **大量 key 同时过期** / Redis 挂了 | TTL 加随机值 + 集群 + 限流 |

1. **缓存穿透**：查不存在的数据，请求直达数据库 → 布隆过滤器、空值缓存、接口限流熔断
2. **缓存雪崩**：大量缓存同时过期，请求直达数据库 → 随机过期时间、互斥锁
3. **缓存击穿**：热点 key 过期瞬间大量并发落 DB → 双重检查锁（DCL）、分布式锁、逻辑过期

**DCL 核心思想**：通过"双重检查 + 分布式锁"确保同一时刻只有一个线程查询数据库。

```java
public String getData(String key) {
    String value = redis.get(key);
    if (value != null) return value;

    if (redis.setnx(lockKey, "1", 10)) {
        try {
            value = redis.get(key);  // 锁内再次检查
            if (value == null) {
                value = database.query(key);
                redis.setex(key, value, 3600);
            }
        } finally {
            redis.del(lockKey);
        }
    } else {
        Thread.sleep(50);
        return getData(key);  // 未获取锁，等待重试
    }
    return value;
}
```

## Redis 有哪些数据类型？

**锚点**：`String/Hash/List/Set/ZSet 五常用 + HyperLogLog/Bitmap 两特殊`

1. **String**：二进制安全，最大 512MB——缓存、计数器
2. **Hash**：键值对集合——对象（用户信息、商品属性）
3. **List**：字符串链表，两端操作——消息队列、最新列表
4. **Set**：无序不重复——标签、共同好友
5. **ZSet**：有序集合按分数排序——排行榜、延迟队列
6. **HyperLogLog**：基数统计内存小——UV 统计
7. **Bitmap**：位图支持位运算——签到、在线状态

## 用 Redis 怎么实现消息队列？

**锚点**：`List 简单队列 / 多 List 优先级 / ZSet 延迟 / Stream 可靠（5.0+）`

1. **List 简单队列**：一端添加一端取，BLPOP 阻塞读取避免轮询
2. **多 List 优先级队列**：消费者按优先级顺序检查不同队列
3. **ZSet 延迟队列**：执行时间作分数，定时扫描到期任务
4. **Stream 可靠队列（5.0+）**：支持消费者组、消息确认、消息回溯

**方案对比**：List 简单高效但消息即删；ZSet 支持延迟；Stream 功能最完善适合可靠队列。

## 如何保证缓存与数据库的一致性？

**锚点**：`先更 DB 后删缓存 / 延迟双删 / MQ 异步，miss 瞬间用 DCL`

1. **脏数据来源**：更新缓存失败、并发读到旧数据
2. **策略**：
   - 更新数据库后删除缓存（下次读时重建）
   - 延迟双删：更新 DB → 删缓存 → 延迟 → 再删缓存
   - MQ 异步更新，保证最终一致性
3. **缓存 miss 瞬间大量请求**：双重检查锁（DCL），同一时刻只有一个线程查库

## Redis 怎么保证数据不丢失？

**锚点**：`混合持久化（RDB+AOF）+ 主从复制 + 哨兵监控`

1. **持久化**：
   - RDB 快照：周期存内存快照，文件小恢复快，可能丢最后一次快照后数据
   - AOF 日志：记所有写操作，最多丢 1 秒，文件大恢复慢
   - 混合持久化（推荐）：RDB + AOF 结合，兼顾恢复速度和安全性
2. **高可用**：主从复制（自动同步）；哨兵模式（监控 + 自动故障转移）；集群模式（分片 + 自动故障转移）

**核心方案**：混合持久化 + 主从复制 + 哨兵监控。

## Redis 的过期删除策略是什么？

**锚点**：`惰性删除（省 CPU 占内存）+ 定期删除（防溢出可能漏删）+ 内存淘汰`

1. **惰性删除**：访问键时检查过期才删——省 CPU 但占内存
2. **定期删除**：定期随机抽部分过期键删除——防内存溢出但可能漏删
3. **内存淘汰策略**（达上限时）：
   - `noeviction`：不删除返回错误（默认）
   - `volatile-lru`：过期键中删最近最少使用
   - `allkeys-lru`：所有键中删最近最少使用
   - `volatile-ttl`：过期键中删剩余时间最短

## Redis 是单线程还是多线程？为什么快？

**锚点**：`6.0 前全单线程，6.0+ 网络 I/O 多线程但命令执行仍单线程`

**快的原因**：

1. 基于内存操作，无磁盘 I/O 延迟
2. 单线程无上下文切换、无锁竞争
3. I/O 多路复用（epoll）高效处理大量连接
4. 精心设计的数据结构（SDS、压缩列表、跳表等）

## Redis 的持久化机制 RDB 和 AOF 有什么区别？

**锚点**：`快照 vs 命令日志；小快 vs 大慢；丢分钟级 vs 丢 1 秒`

| 对比项 | RDB | AOF |
|--------|-----|-----|
| 存储内容 | 内存快照 | 写操作命令 |
| 文件大小 | 小 | 大 |
| 恢复速度 | 快 | 慢 |
| 数据安全性 | 可能丢几分钟 | 最多丢 1 秒 |
| 适用场景 | 允许少量丢失、求恢复速度 | 数据安全要求高 |

**生产推荐**：开启混合持久化，RDB 做 baseline，AOF 追加增量命令。

## Redis 如何实现分布式锁？

**锚点**：`SET NX PX 加锁 + Lua 脚本验值释放 + 看门狗续期，集群用 Redisson`

**基本实现**：

```bash
SET lock:resource unique_value NX PX 30000
# NX 不存在才设置，PX 过期时间
```

**释放锁**（Lua 保证原子性）：

```lua
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end
```

**注意事项**：设置过期时间防死锁；释放要验证是自己持有（unique_value）；考虑锁续期（看门狗）；集群环境下建议用 Redisson。

## Redis 集群方案有哪些？

**锚点**：`主从（手动切换）/ 哨兵（自动转移）/ Cluster（分片 + 自动转移）`

1. **主从复制**：一主多从、读写分离，故障需手动切换
2. **哨兵模式**：监控 + 自动故障转移，但单节点内存受限
3. **Cluster 集群**：数据分片 + 自动故障转移，水平扩展

**Cluster 原理**：16384 个槽位均匀分配到各节点；客户端重定向（MOVED/ASK）；Gossip 协议节点通信。

## 什么是缓存预热？缓存热点 Key？

**锚点**：`预热：启动前提前加载热点；热点 Key：发现 + 拆分 + 多级缓存`

1. **缓存预热**：系统启动前提前加载热点数据，避免启动时大量请求穿透到 DB
2. **热点 Key 处理**：监控访问频率自动发现；加随机后缀拆分散到多个 Key；本地缓存 + Redis 多级缓存

## Redis 事务了解吗？

**锚点**：`MULTI/EXEC/DISCARD/WATCH：顺序执行、不支持回滚、WATCH 乐观锁`

1. 事务中的命令按顺序执行，不会被其他客户端打断
2. 不支持回滚，某条命令失败不影响后续执行
3. WATCH 实现乐观锁，监听的 Key 被修改则事务失败

```bash
WATCH key          # 监听 Key
MULTI              # 开启事务
SET key value
INCR counter
EXEC               # 执行事务（或 DISCARD 取消）
```

## Redis 如何处理大 Key？

**锚点**：`危害：阻塞/网络慢/内存不均/删除久；方案：拆分、压缩、本地缓存、UNLINK`

1. **大 Key 定义**：Value 过大（1MB+）、集合元素过多（百万级）
2. **危害**：网络传输慢阻塞请求、内存不均匀影响分片、过期删除耗时长
3. **解决**：大集合拆小集合；压缩算法减小体积；不频繁变化的大 Key 放本地缓存；`UNLINK` 异步删除

## Redis 为什么用跳表不用 B+ 树？

**锚点**：`内存场景：性能相当但实现更简单，范围查询友好，层数可调`

1. 内存场景性能与平衡树相当，但跳表实现更简单
2. 有序链表结构天然支持范围查询
3. 层数按需调整，内存占用更省
4. 比 B+ 树更容易实现和维护

B+ 树更适合磁盘存储，跳表更适合内存存储。

## Redis 持久化有哪两种方式？

**锚点**：`RDB 全量快照 vs AOF 追加命令；生产两者都开`

| | RDB | AOF |
|---|---|---|
| 原理 | 内存数据全量快照，存 `dump.rdb` | 每条写命令追加到 `appendonly.aof` |
| 触发 | `save 900 1`（900s ≥1 次修改）等组合条件 | `appendfsync`：always/everysec/no |
| 数据完整度 | 两次快照间数据可能丢 | 高（everysec 最多丢 1s） |
| 恢复速度 | 文件小、恢复快 | 文件大、恢复慢（重跑所有命令） |

生产环境：两者都开，AOF 优先恢复保证完整，RDB 做冷备。

## RDB 和 AOF 各自优缺点是什么？

**锚点**：`RDB 小快但丢数据；AOF 完整但大慢`

- **RDB**：文件小恢复快，但两次快照间数据可能丢
- **AOF**：数据完整度高（everysec 最多丢 1s），但文件大恢复慢

## 缓存穿透怎么解决？布隆过滤器原理？

**锚点**：`布隆：bit 数组 + 多 hash——有一个 bit 为 0 则一定不存在；全 1 才可能存在`

1. **穿透**：查**不存在**的数据，缓存和 DB 都没有
2. **布隆过滤器原理**：bit 数组 + 多个 hash 函数；写入把对应 bit 置 1；查询时只要有一个 bit 为 0 则 key **一定不存在**（直接拦截），全为 1 可能存在（有误判率）
3. **其他方案**：缓存空值（TTL 短）
4. **三兄弟区分**：穿透 = 查不存在的数据；击穿 = 热点 key 过期瞬间高并发打 DB；雪崩 = 大量 key 同时过期或 Redis 挂了
