## Redis 缓存穿透、缓存雪崩和缓存击穿分别是什么？如何解决？

1. **缓存穿透**：查询不存在的数据，请求直达数据库。
   - 解决方案：布隆过滤器、空值缓存、接口限流与熔断

2. **缓存雪崩**：大量缓存同时过期，请求直达数据库。
   - 解决方案：随机过期时间、互斥锁

3. **缓存击穿**：热点key过期瞬间，大量并发请求同时落DB。
   - 解决方案：双重检查锁(DCL)、分布式锁、逻辑过期

**双重检查锁(DCL)核心思想**：通过"双重检查 + 分布式锁"确保同一时刻只有一个线程查询数据库。

```java
public String getData(String key) {
    String value = redis.get(key);
    if (value != null) return value;

    if (redis.setnx(lockKey, "1", 10)) {
        try {
            value = redis.get(key);  // 锁内再次检查
            if (value == null) {
                value = database.query(key);
                redis.setex(key, value, 3600);
            }
        } finally {
            redis.del(lockKey);
        }
    } else {
        Thread.sleep(50);
        return getData(key);  // 未获取锁，等待重试
    }
    return value;
}
```

## Redis 有哪些数据类型？

1. **String**：二进制安全，最大512MB。典型场景：缓存、计数器
2. **Hash**：键值对集合，适合存储对象。典型场景：用户信息、商品属性
3. **List**：字符串链表，支持两端操作。典型场景：消息队列、最新列表
4. **Set**：无序不重复集合。典型场景：标签、共同好友
5. **ZSet**：有序集合，按分数排序。典型场景：排行榜、延迟队列
6. **HyperLogLog**：基数统计，内存占用小。典型场景：UV统计
7. **Bitmap**：位图，支持位运算。典型场景：用户签到、在线状态

## 用 Redis 怎么实现消息队列？

1. **List 实现简单队列**：一端添加，另一端取出，使用 BLPOP 阻塞读取避免轮询。
2. **多 List 实现优先级队列**：消费者按优先级顺序检查不同队列。
3. **ZSet 实现延迟队列**：将执行时间作为分数，定时扫描到期任务。
4. **Stream 实现可靠队列（Redis 5.0+）**：支持消费者组、消息确认、消息回溯。

**方案对比**：
- List：简单高效，但消息即删，适合简单任务分发
- ZSet：支持延迟执行，适合定时任务
- Stream：功能最完善，适合可靠消息队列

## 如何保证缓存与数据库的一致性？

**脏数据产生原因**：
- 更新缓存失败导致不一致
- 并发操作导致读到旧数据

**常用策略**：
1. **更新数据库后删除缓存**：下次读取时从数据库重新加载
2. **延迟双删**：更新DB → 删缓存 → 延迟 → 再删缓存
3. **基于消息队列**：通过MQ异步更新，保证最终一致性

**缓存 miss 瞬间大量请求怎么办？** 采用双重检查锁(DCL)，确保同一时刻只有一个线程查询数据库。

## Redis 怎么保证数据不丢失？

**持久化机制**：
1. **RDB快照**：周期性保存内存快照，文件小、恢复快，但可能丢失最后一次快照后的数据
2. **AOF日志**：记录所有写操作，最多丢失1秒数据，文件大、恢复慢
3. **混合持久化（推荐）**：RDB+AOF结合，兼顾恢复速度和数据安全性

**高可用机制**：
1. **主从复制**：数据自动同步到从节点
2. **哨兵模式**：监控集群，自动故障转移
3. **集群模式**：数据分片+自动故障转移

**核心方案**：混合持久化 + 主从复制 + 哨兵监控。

## Redis 的过期删除策略是什么？

Redis 使用两种策略结合：

1. **惰性删除**：访问键时检查是否过期，过期则删除。节省CPU但可能占用内存。
2. **定期删除**：定期随机抽取部分过期键检查删除。防止内存溢出但可能漏删。

**内存淘汰策略**（内存达上限时）：
- `noeviction`：不删除，返回错误（默认）
- `volatile-lru`：从过期键中删除最近最少使用的
- `allkeys-lru`：从所有键中删除最近最少使用的
- `volatile-ttl`：从过期键中删除剩余时间最短的

## Redis 是单线程还是多线程？为什么快？

Redis 核心网络模型在 6.0 之前是单线程，6.0 之后引入多线程处理网络 I/O，但命令执行仍是单线程。

**快的原因**：
1. 基于内存操作，无磁盘 I/O 延迟
2. 单线程无上下文切换开销，无锁竞争
3. I/O 多路复用（epoll），高效处理大量连接
4. 精心设计的数据结构（SDS、压缩列表、跳表等）

## Redis 的持久化机制 RDB 和 AOF 有什么区别？

| 对比项 | RDB | AOF |
|--------|-----|-----|
| 存储内容 | 内存快照 | 写操作命令 |
| 文件大小 | 小 | 大 |
| 恢复速度 | 快 | 慢 |
| 数据安全性 | 可能丢失几分钟数据 | 最多丢失1秒 |
| 适用场景 | 允许少量丢失、追求恢复速度 | 数据安全要求高 |

**生产推荐**：开启混合持久化，RDB 做 baseline，AOF 追加增量命令。

## Redis 如何实现分布式锁？

**基本实现**：
```bash
SET lock:resource unique_value NX PX 30000
# NX 表示不存在才设置，PX 设置过期时间
```

**释放锁**（Lua 脚本保证原子性）：
```lua
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end
```

**注意事项**：
1. 设置过期时间防止死锁
2. 释放锁要验证是自己持有的（unique_value）
3. 考虑锁续期问题（看门狗机制）
4. 集群环境下可能不安全，建议用 Redisson

## Redis 集群方案有哪些？

1. **主从复制**：一主多从，读写分离，故障需手动切换
2. **哨兵模式**：监控+自动故障转移，但单节点内存受限
3. **Cluster 集群**：数据分片+自动故障转移，支持水平扩展

**Cluster 原理**：
- 16384 个槽位均匀分配到各节点
- 客户端重定向（MOVED/ASK）
- Gossip 协议进行节点通信

## 什么是缓存预热？缓存热点 Key？

**缓存预热**：系统启动前提前加载热点数据到缓存，避免启动时大量请求穿透到数据库。

**缓存热点 Key**：
1. 热点 Key 自动发现：监控访问频率
2. 热点 Key 拆分：加随机后缀分散到多个 Key
3. 本地缓存 + Redis 多级缓存

## Redis 事务了解吗？

Redis 事务通过 MULTI、EXEC、DISCARD、WATCH 命令实现。

**特点**：
1. 事务中的命令按顺序执行，不会被其他客户端打断
2. 不支持回滚，某条命令失败不影响后续命令执行
3. WATCH 实现乐观锁，监听的 Key 被修改则事务失败

```bash
WATCH key          # 监听 Key
MULTI              # 开启事务
SET key value
INCR counter
EXEC               # 执行事务（或 DISCARD 取消）
```

## Redis 如何处理大 Key？

**大 Key 问题**：
- 单个 Key 的 Value 过大（如 1MB 以上）
- 集合元素过多（如 List 有百万元素）

**危害**：
- 网络传输慢，阻塞其他请求
- 内存不均匀，影响集群分片
- 过期删除耗时长

**解决方案**：
1. **拆分**：大集合拆成多个小集合
2. **压缩**：使用压缩算法减小体积
3. **本地缓存**：不频繁变化的大 Key 放本地
4. **异步删除**：UNLINK 命令异步删除

## Redis 为什么用跳表不用 B+ 树？

1. **内存场景更高效**：跳表在内存中性能与平衡树相当，但实现更简单
2. **范围查询友好**：跳表的有序链表结构天然支持范围查询
3. **内存占用更少**：跳表可以根据需要调整层数
4. **实现简单**：跳表比 B+ 树更容易实现和维护

B+ 树更适合磁盘存储，跳表更适合内存存储。
