## 说一下你对MySQL的理解？

**锚点**：`最流行关系型数据库：一致性 + 查询强 + 生态成熟 + 免费`

1. **数据一致性**：事务保证数据准确性
2. **查询能力强**：SQL 支持复杂关联查询
3. **生态成熟**：工具丰富，社区支持完善
4. **成本低**：开源免费

## MySQL 的事务四大特性（ACID）是什么？

**锚点**：`原子性、一致性、隔离性、持久性`

1. **原子性（Atomicity）**：事务要么全成功要么全失败
2. **一致性（Consistency）**：执行前后数据保持一致
3. **隔离性（Isolation）**：事务间互不干扰
4. **持久性（Durability）**：事务提交后数据永久保存

## Mysql的索引有哪些类型？什么时候使用？

**锚点**：`数据结构（B+Tree/Hash/全文）× 逻辑特性（主键/唯一/普通/联合）`

1. **按数据结构**：
   - B+Tree：InnoDB 默认，支持范围查询和排序
   - Hash：Memory 引擎，等值查询极快，不支持范围
   - 全文：FULLTEXT，文本搜索（5.6+ 支持 InnoDB）
2. **按逻辑特性**：
   - 主键索引：唯一标识，不允许 NULL，一张表一个
   - 唯一索引：列值唯一，允许 NULL，可有多个
   - 普通索引：无约束，提高查询速度
   - 联合索引：多列组合，遵循最左前缀原则
3. **使用场景**：频繁作 WHERE、JOIN、ORDER BY 条件的字段；避免在频繁更新、低选择性列上建索引

## 怎么知道查询有没有走索引？

**锚点**：`EXPLAIN 看执行计划：type 别是 all，key 是实际索引`

1. **EXPLAIN**：SQL 前加 EXPLAIN 查看执行计划
2. **type 列**：ref、range、index、all（all = 全表扫描，未用索引）
3. **key 列**：实际使用的索引；**possible_keys**：可能使用的索引

## 索引什么时候会失效？

**锚点**：`八种：破最左前缀、函数/运算、类型转换、否定、OR、%开头、NULL、列运算`

1. 违反最左前缀原则（联合索引未用最左列）
2. WHERE 中对索引列做函数操作
3. 类型转换（索引列与查询值类型不匹配）
4. 使用 `!=`、`<>`、`NOT IN` 等否定条件
5. OR 连接且一边无索引
6. LIKE 以 `%` 开头
7. 条件含 IS NULL / IS NOT NULL
8. 索引列参与运算（如 `WHERE a+1=10`）

## 大量数据应该怎么样查询？

**锚点**：`分页 + 索引 + 分库分表 + 读写分离 + 缓存 + 覆盖索引`

1. 分页查询：LIMIT + 合理 ORDER BY，避免 OFFSET 过大
2. 索引优化：为查询条件、排序字段建合适索引
3. 分表分库：按时间、地域等维度拆分
4. 读写分离：主库写、从库读，分担查询压力
5. 缓存优化：Redis 缓存热点数据
6. 减少返回字段：避免 SELECT *
7. 批量处理：大查询拆小批量
8. 覆盖索引：查询只需索引列，无需回表

> **覆盖索引**：索引包含查询所需的所有列，直接取数据，无需回表查数据行。

## 说一下b+树的索引结构，Mysql为什么选用b+树？

**锚点**：`多路平衡查找树：矮胖省 I/O、叶子链表范围快、路径稳定`

1. **B+ 树特点**：多路结构减树高；所有叶子同层查询稳定；叶子节点间指针相连
2. **B 树 vs B+ 树**：

| 对比 | B 树 | B+ 树 |
|------|------|-------|
| 数据存放 | 所有节点都存 | 只有叶子存完整数据 |
| 叶子关系 | 独立无连接 | 指针连成有序链表 |
| 查询稳定 | 不稳定 | 稳定到最底层 |
| 范围查询 | 来回跳转慢 | 顺链表走快 |
| 节点利用 | 存数据+指针，关键字少 | 只存指针，关键字多 |

3. **MySQL 选 B+ 树**：磁盘 I/O 少（矮胖）；范围查询高效（链表）；查询性能稳定（路径等长）；内存利用高效（非叶子只存索引）

**比喻**：B 树像传统图书馆每层书架都有书；B+ 树像现代图书馆，目录层只有索引卡片，书全在一楼按编号连续排列。

## MySQL 的存储引擎有哪些？默认使用哪个？

**锚点**：`InnoDB 默认（事务+行锁），MyISAM 读多写少，Memory 内存表`

- **InnoDB**（默认）：支持事务、行级锁、外键，适合高并发业务
- **MyISAM**：不支持事务，表级锁，适合读多写少
- **Memory**：存内存中，速度极快，适合临时数据

```sql
CREATE TABLE users (id int) ENGINE=InnoDB;
```

## InnoDB 是如何存储数据的？

**锚点**：`三层：表空间 → 页(16KB) → 行；主键聚簇、二级索引回表`

1. **三层结构**：表空间（大容器）→ 页（16KB，磁盘读写基本单位）→ 行
2. **聚簇索引**：表数据本身就是按主键组织的 B+ 树
   - 主键索引：叶子存**整行数据**
   - 二级索引：叶子存**主键值**，查完整数据要"回表"

## MySQL为啥不推荐用text字段？

**锚点**：`检索慢、占空间、索引支持有限、维护成本高`

**原因**：检索慢（存溢出页）、占空间大、索引支持有限、维护成本高

**替代方案**：VARCHAR、拆分表、存文件路径、用 MongoDB

## 为什么MySQL用B+树，MongoDB用B树?

**锚点**：`MySQL 重范围查询（链表扫描）；MongoDB 重单键查询（中间节点可取数据）`

1. **MySQL 选 B+ 树**：范围查询高效（叶子链表）；查询稳定（路径等长）；I/O 少（非叶子只存索引）；关系型数据多范围查询排序
2. **MongoDB 选 B 树**：文档数据大，节点可直接存完整文档；单键查询更快（中间节点即可命中）；对复杂数据类型更灵活；NoSQL 多为键值查询

## MySQL热点数据更新会带来哪些问题，如何优化？

**锚点**：`问题：锁竞争/超时/吞吐降/击穿；方案：分片+缓存+异步+乐观锁+读写分离`

1. **问题**：单行锁竞争、事务超时、吞吐下降、缓存击穿
2. **解决**：分库分表、多级缓存、MQ 异步化、乐观锁、读写分离

## 如果要存IP地址，用什么数据类型比较好？

**锚点**：`INT UNSIGNED + INET_ATON/NTOA，IPv6 用 VARBINARY(16)`

推荐 `INT UNSIGNED`——节省空间、查询效率高。

```sql
INSERT INTO users (ip) VALUES (INET_ATON('192.168.1.1'));
SELECT INET_NTOA(ip) FROM users;
```

IPv6：`VARBINARY(16)` 或 `BINARY(16)`，配合 `INET6_ATON()` / `INET6_NTOA()`。

## 数据库性能瓶颈如何优化？

**锚点**：`查询优化 → 架构优化 → 缓存 → 硬件`

- **查询优化**：索引、避免 SELECT *、JOIN 替代子查询
- **架构优化**：读写分离、分库分表、引入 ES
- **缓存优化**：Redis 缓存热点数据
- **硬件优化**：增加内存、使用 SSD

## 不停服数据迁移怎么做？

**锚点**：`双写 + 灰度切换：全量 → 双写 → 灰度切读 → 全切 → 清理`

全量迁移 → 双写同步 → 灰度切读 → 完全切换 → 清理旧表

## 如何优化 SQL 性能？

**锚点**：`索引 + 免 SELECT * + EXPLAIN + JOIN 替代子查询 + LIMIT`

1. 使用合适索引，避免全表扫描
2. 避免 SELECT \*，只查必要字段
3. 用 `EXPLAIN` 查看执行计划
4. 避免子查询，尽量用 JOIN
5. 控制返回行数，分页加 LIMIT

## `OVER` 与 `GROUP BY` 的区别？

**锚点**：`GROUP BY 分组聚合减行数；OVER 窗口计算不减少行`

| 特性 | GROUP BY | OVER（窗口函数） |
|------|----------|-----------------|
| 作用方式 | 分组后聚合，每组一行 | 逐行计算，不减少行数 |
| 返回行数 | 比原表少 | 与原表相同 |
| 适用场景 | 只关心组聚合结果 | 保留明细 + 附分析值 |
| 列限制 | 只能出现分组字段或聚合函数 | 任意字段 |

```sql
-- GROUP BY：每个部门一行
SELECT department_id, SUM(salary) FROM employees GROUP BY department_id;
-- OVER：每行保留员工 + 所在部门总工资
SELECT employee_name, department_id,
       SUM(salary) OVER (PARTITION BY department_id) AS dept_total
FROM employees;
```

## SQL语句关键字顺序和执行顺序？

**锚点**：`关键字：SELECT→FROM→WHERE→GROUP BY→HAVING→ORDER BY→LIMIT；执行：FROM→WHERE→GROUP BY→HAVING→SELECT→ORDER BY`

1. **关键字顺序**：SELECT → FROM → WHERE → GROUP BY → HAVING → ORDER BY → LIMIT
2. **执行顺序**：FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY

## 一条 SQL 在 MySQL 中的执行过程？

**锚点**：`连接器 → 解析器 → 优化器 → 执行器 → 存储引擎`

1. **连接器**：TCP 连接，验证账号密码和权限
2. **查询缓存**（8.0 移除）：查相同 SQL 的缓存结果
3. **解析器**：词法/语法分析，生成解析树
4. **优化器**：选最优执行计划（索引、连接顺序）
5. **执行器**：调存储引擎接口执行，校验表/字段权限
6. **存储引擎**：InnoDB/MyISAM 真正读写数据
7. **返回结果**：数据逐层返回客户端

## 为什么数据库连接很消耗资源？

**锚点**：`TCP 握手 + 认证 + 资源分配，频繁创建销毁开销大`

需要 TCP 握手、身份认证、资源分配，频繁创建/销毁开销大，所以用连接池复用。

## 什么是数据库连接池？

**锚点**：`预先建连接复用；HikariCP 推荐 / Druid 全面 / C3P0 较老`

预先创建连接并复用，降低连接开销。常见实现：HikariCP（推荐，轻量高效）、Druid（阿里开源，功能全面）、C3P0（较老，配置复杂）。

## 连接池如何降低开销？

**锚点**：`复用已有连接，统一管理数量`

避免频繁建立/关闭连接，复用已有连接，统一管理连接数量。

## 连接池如何实现？

**锚点**：`初始化 → 获取 → 使用 → 归还；核心：最大连接数、空闲检测、保活、等待队列`

初始化创建连接 → 获取连接 → 使用 → 归还连接池。核心机制：最大连接数、空闲检测、连接保活、等待队列。

## 如何分析MySQL慢查询？

**锚点**：`开慢日志 → 分析工具 → EXPLAIN 定位 → 常见原因对症下药`

1. **开启慢查询日志**：`SET GLOBAL slow_query_log = ON;` + `long_query_time = 1`（超 1 秒记录）
2. **分析日志**：`mysqldumpslow -s t -t 10 slow.log`（按时间前 10 条）；`pt-query-digest slow.log` 更详细
3. **定位问题 SQL**：EXPLAIN 关注 `type=ALL`、`key`；`SHOW PROFILE` 看各阶段耗时
4. **常见原因**：未用索引或失效、SELECT * 过大、深度分页、子查询低效
5. **优化手段**：为 WHERE/JOIN/ORDER BY 建索引、只查必要字段、深度分页改游标、子查询改 JOIN、大表分库分表

## 聚簇索引和回表是什么意思？

**锚点**：`主键索引叶子存整行 = 聚簇；二级索引只存主键，查完整行要回表`

1. **聚簇索引**：InnoDB 主键索引，叶子存整行数据，一张表只有一个
2. **回表**：二级索引叶子只存主键 ID，查到 ID 再去聚簇索引查一次拿完整行——多一次随机 IO
3. **覆盖索引**：查询列全在索引里，不用回表，EXPLAIN Extra 显示 `Using index`

## 什么是覆盖索引？为什么能优化查询？

**锚点**：`查询列全在索引里，直接从索引返回，少一次回表 IO`

1. 查询的所有列都在索引里，直接从索引返回，不需要回表查聚簇索引
2. 少一次 IO，所以快
3. 做法：SELECT 只查需要的列，建联合索引覆盖这些列

## redo log 和 binlog 有什么区别？

**锚点**：`引擎层 vs Server 层；物理 vs 逻辑；循环写 vs 追加写；崩溃恢复 vs 主从复制`

1. **归属**：redo log 是 InnoDB 引擎层；binlog 是 MySQL Server 层
2. **内容**：redo log 是物理日志（哪个页哪个偏移量改什么）；binlog 是逻辑日志（SQL 语句或行级变更）
3. **写方式**：redo log 循环写、固定大小写满覆盖；binlog 追加写、写满切新文件
4. **用途**：redo log 做崩溃恢复（Crash Recovery）保事务持久性；binlog 做主从复制 + 时间点恢复
5. **落盘时机**：事务提交时两者都 fsync 刷盘后才返回成功
6. **两阶段提交**：redo log prepare → 写 binlog → redo log commit，保证两份日志一致，崩溃后能判断回滚还是提交
