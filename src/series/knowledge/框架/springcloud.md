## 什么是微服务？有哪些优缺点？

**锚点**：`单体拆多服务独立部署；优点开发/部署/扩展独立，缺点复杂/测试难/运维贵`

微服务是将单体应用拆分成多个独立服务，各服务可独立部署、扩展。

- **优点**：开发独立、部署灵活、可按需扩展
- **缺点**：系统复杂、测试困难、运维成本高、接口通信开销大

## 每个微服务之间如何通信？

**锚点**：`同步（HTTP/RPC）强一致实时；异步（MQ）解耦削峰`

1. **同步通信**：HTTP 或 RPC——OpenFeign、RestTemplate、Dubbo、gRPC；实时响应，适合强一致性场景
2. **异步通信**：消息队列——Kafka、RabbitMQ、RocketMQ；解耦、削峰填谷，适合异步处理

## ⭐微服务四大件都有哪些？

**锚点**：`注册发现 + 配置中心 + 网关 + 通信容错`

1. **服务注册与发现**：管理服务地址，自动注册发现——Nacos、Eureka、Consul、Zookeeper
2. **配置中心**：集中管理配置，支持热更新——Nacos、Apollo、Spring Cloud Config
3. **服务网关**：统一入口，路由转发、权限校验、限流熔断——Gateway、Zuul、Kong、Nginx
4. **服务通信与容错**：服务间调用 + 熔断限流重试——OpenFeign、Dubbo、gRPC（通信）；Sentinel、Resilience4j、Hystrix（容错）

## Nacos 如何实现配置热更新？

**锚点**：`长轮询监听 + 服务端推送 + @RefreshScope 刷新`

1. **长轮询监听**：客户端开启长轮询，实时监听配置中心变更
2. **事件通知**：服务端配置变化时主动推送通知客户端
3. **@RefreshScope**：Spring Cloud 中该注解让 Bean 在配置更新时动态刷新
4. **配置绑定**：`@Value` 或 `@ConfigurationProperties` 绑定属性，配合 `@RefreshScope` 实现热更新

## Hystrix 和 Sentinel 有什么区别？

**锚点**：`Hystrix 已停维护只管熔断降级；Sentinel 功能全：限流+熔断+降级+控制台`

- **Hystrix**：Netflix 断路器组件，服务熔断、降级、隔离——已停止维护
- **Sentinel**：阿里开源流量防护，功能更全——限流、熔断、降级、热点参数限流、系统自适应保护，提供控制台可视化管理

## 如何监控微服务中的负载均衡状态？

**锚点**：`日志看分布 / 注册中心看健康 / 链路追踪看耗时 / Prometheus 看指标`

1. **应用日志**：调用层打印目标实例信息，追踪请求分配
2. **LoadBalancer/Ribbon**：开 debug 日志或结合 Actuator 查看调用分布
3. **注册中心**：Nacos/Eureka 控制台看实例健康状态和权重
4. **链路追踪**：Sleuth + Zipkin / SkyWalking 监控请求分布和耗时
5. **指标监控**：Prometheus + Grafana 采集调用指标，直观展示负载均衡效果

## Spring Boot Admin的作用是什么？

**锚点**：`管理和监控 Spring Boot 应用的统一 Web 界面`

- 服务监控：实时监控健康状态、内存、CPU
- 日志管理：在线查看和修改日志级别
- JVM 监控：监控内存、线程、GC
- 配置管理：查看和修改应用配置
- 告警通知：服务异常时发送告警
- 统一界面：管理多个微服务实例

## 为什么需要微服务监控中心？

**锚点**：`全局视图 + 快速定位 + 性能优化 + 容量规划 + 自动化运维`

- 全局视图：所有服务的统一监控视图
- 故障排查：快速定位问题服务实例
- 性能优化：通过监控数据发现性能瓶颈
- 容量规划：根据历史数据预测容量
- 自动化运维：结合告警系统自动化运维
- 服务治理：监控服务间调用关系和依赖

## 如何实现服务状态变更的告警？

**锚点**：`监听 → 过滤 → 策略 → 多通道 → 去重 → 升级`

- **事件监听**：监听服务实例状态变化事件
- **状态过滤**：过滤不重要变化（如 DOWN 恢复 UP）
- **告警策略**：定义触发条件和频率
- **多通道通知**：邮件、短信、钉钉、企业微信
- **告警去重**：避免重复告警
- **告警升级**：持续未处理的告警升级处理

## 在微服务中，为什么业务配置放在配置中心，而配置中心的连接信息放在本地 bootstrap.yml 中？

**锚点**：`先连得上配置中心，才能读业务配置——引导配置必须本地`

你必须先能连上"配置中心"，才能从配置中心读取业务配置。所以连接配置中心的最小启动配置 bootstrap.yml 必须放本地。

## 为什么 Nacos 配置表的 context 字段用 LONGTEXT 而不是 JSON？

**锚点**：`格式多样 + 跨库兼容 + 无校验性能好`

1. 配置内容格式多样（YAML、Properties、XML、JSON），JSON 字段会触发数据库 JSON 校验，限制格式
2. 要兼容多种数据库（MySQL、MariaDB、PostgreSQL），各库 JSON 类型实现不一致
3. LONGTEXT 全库支持、无校验、兼容性最好、写入性能更高

## `debug: true` 为什么不能放在 bootstrap.yml 中？必须放在 application.yml 中才能生效？

**锚点**：`debug 要启动早期生效，而远程配置加载太晚`

1. **时机问题**：debug 需启动早期生效以捕获启动问题；Nacos 远程配置获取需要时间，启动时还没加载到
2. **加载顺序**：bootstrap.yml 连接配置中心 → 本地 application.yml 立即生效 → 远程 application.yml 后期加载（错过时机）
3. **结论**：`debug: true` 必须放本地 application.yml

## Nacos 远程配置变更后，服务需要重启吗？

**锚点**：`只有 @RefreshScope 的 Bean 能热更新，其他都得重启`

1. **加了 @RefreshScope 的 Bean**：不需要重启，自动刷新
2. **普通 Bean**：需要重启，配置变更影响不了已创建的 Bean
3. **连接配置中心的地址变更**：必须重启
4. **bootstrap.yml 中的配置**：必须重启

## 服务 A Feign 调用服务 B，B 挂了怎么发现和兜底？

**锚点**：`Nacos 心跳剔除发现，Sentinel 熔断降级兜底`

- **发现**：Nacos 心跳检测，B 挂了踢出服务列表，A 拉取最新实例列表
- **兜底**：Sentinel 熔断降级——调 B 失败率达标 → 熔断器打开 → 后续请求直接走 fallback（返回兜底数据）→ 定时半开探测 → 恢复则关闭熔断

负载均衡只在多实例可用时有意义，所有实例全挂时熔断是最后防线。

## Sentinel 熔断、降级、限流分别是什么意思？熔断策略有哪几种？

**锚点**：`熔断快速失败保护自己、降级返回兜底、限流控 QPS；三策略：慢调用/异常比例/异常数`

**概念**：

- **熔断**：下游调用失败率达阈值 → 熔断器打开 → 后续请求**快速失败**不调下游 → 窗口期后半开试探 → 成功则关闭。保护自己不被下游拖垮
- **降级**：服务不可用时**返回兜底结果**（fallback）——缓存数据、默认值、空列表，保证主流程
- **限流**：控制 QPS/并发数，超阈值直接拒绝，保护系统不被冲垮

**熔断三种状态**：关闭（正常）→ 开启（熔断中，快速失败）→ 半开（试探一次，成功则关闭，失败则继续开启）

**Sentinel 熔断策略**：

1. **慢调用比例**：响应时间超过阈值的调用占比过高
2. **异常比例**：异常数占总调用数比例过高
3. **异常数**：异常数超过阈值
