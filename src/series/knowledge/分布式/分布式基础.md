# 分布式基础

## CAP 定理是什么？Nacos AP 和 CP 怎么选？

**锚点**：`P 必选，C/A 二选一；Nacos 临时实例 AP、持久实例 CP`

1. **C**onsistency 一致性：所有节点同一时刻数据一致
2. **A**vailability 可用性：每次请求都能收到响应
3. **P**artition tolerance 分区容错：网络分区时系统仍能工作
4. **取舍**：P 必须选，所以实际是 CP 或 AP 二选一
5. **Nacos 对应**：临时实例（AP，强调可用）、持久实例（CP，强调一致），按场景切换

## 为什么在分布式系统中需要全局唯一 ID？

**锚点**：`单机自增在分库分表/高并发下会重复，需要全局唯一、有序、高性能`

1. **问题**：分库分表、高并发场景下只依赖单机自增 ID，容易重复冲突，难以保证数据唯一性和可追踪性
2. **需求**：不同机器、不同库表生成的 ID 要**全局唯一、有序、性能高**

## 分布式 ID 生成的常见方案有哪些？

**锚点**：`五选一：号段 / UUID / 雪花 / Redis 自增 / 开源中间件`

1. **数据库号段（Segment）**：一次取一段（如 1000 个）缓存在内存本地生成——简单、有序；依赖数据库、有单点
2. **UUID**：本地生成随机字符串——无中心化依赖；冗长、无序、查询性能差
3. **Snowflake 雪花算法**：时间戳 + 数据中心 ID + 机器 ID + 自增序列——高性能、趋势递增、常用；时钟回拨、机器 ID 配置复杂
4. **Redis / Zookeeper 自增**：分布式缓存/协调器生成——一致性强；性能瓶颈、可用性依赖
5. **开源中间件**：百度 UidGenerator、美团 Leaf——支持号段和雪花，工业级稳定

## ❄️ 雪花算法会有哪些问题？如何解决？

**锚点**：`四大问题：时钟回拨 / 机器 ID 重复 / 写入热点 / 扩展受限`

1. **时钟回拨**：ID 前 41 位是时间戳，要求单调递增；NTP 回拨几秒导致时间戳倒退，新 ID 可能比旧 ID 小甚至冲突
   - 解决：检测回拨并等待追上、ID 加回拨标记位、NTP 定时校时、持久化上次时间戳发现回拨拒绝生成
2. **机器 ID 重复**：10 位机器 ID 配置不当导致两节点一致，同一毫秒生成的 ID 完全冲突
   - 解决：注册中心（ZK/Etcd/Nacos）动态分配、启动时向 DB/Redis 申请 Worker ID 并续约、按 MAC/IP 自动计算
3. **写入热点**：ID 趋势递增，大量数据集中写索引最后一页
   - 解决：序列号加随机因子打散、预留混淆位、结合分库分表路由
4. **扩展受限**：41 位时间戳（69 年）/ 10 位机器（1024 节点）/ 12 位序列（每毫秒 4096 个）
   - 解决：调整位数分配、多集群前缀区分、结合号段模式减少单毫秒压力
