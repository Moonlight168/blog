# LangChain 面试题

## LangChain 是什么？核心价值在哪？

LangChain 是 LangChain 团队推出的 LLM 应用开发框架，核心价值我概括成三点：

1. **统一了 LLM 的调用抽象**：不管你接 OpenAI、Claude 还是别的模型，都是同一套接口，换模型不用改业务代码。
2. **把常见能力做成了组件**：Prompt 管理、模型调用、输出解析、检索（Retriever）、记忆、工具调用这些都有标准组件，拼装就能用。
3. **生态大**：LangChain 的社区和集成是最广的，文档、第三方集成、AI 应用基本绕不开它。

但我也会补一句实话：**LangChain 早期被吐槽太抽象、太绕**，简单功能写出来的代码比直接调 API 还长。所以现在更主流的选择是 LangGraph（编排）或直接调模型，LangChain 的定位越来越偏"组件库"。

---

## LangChain 和 LangGraph 是什么关系？各自解决什么问题？

这俩是 LangChain 团队的两代产品，定位完全不同：

1. **LangChain 是组件库**：模型、Prompt、Retriever、Memory、Tool 这些现成组件，适合快速拼一个相对线性的应用。
2. **LangGraph 是编排引擎**：专门做"图"式的有状态编排——节点、边、状态、循环、条件路由，适合复杂工作流和 Agent。它是在 LangChain 组件之上的一层编排框架。

一句话区分：**LangChain 给你积木，LangGraph 给你搭复杂结构的图纸**。简单应用用 LangChain 够，复杂流程、需要循环和状态管理的用 LangGraph。

---

## Chain 和 Agent 有什么区别？

一句话点破本质：**Chain 是"写死的流程"，Agent 是"模型自己决策的流程"**。

1. **Chain**：每个步骤是确定的，先做 A 再做 B 再做 C，模型只在每步内部做有限输出。可预期、稳定、好调试。
2. **Agent**：给模型目标，它自己决定调哪个工具、走哪条路，还可以根据结果回头调整。灵活、上限高，但结果不稳定、要防死循环。

实际选型：**业务规则清楚就用 Chain，需要模型自己探索和决策就用 Agent**。现在很多应用是"Chain 打底 + 关键节点给 Agent 自主"的混合。

---

## LCEL（LangChain Expression Language）是什么？为什么用它？

LCEL 是 LangChain 的表达式语言，用 `|` 管道符把组件串起来，我理解它主要解决三个问题：

1. **声明式组装**：用一条管道就把"Prompt → 模型 → 输出解析"串完，代码比手写每步简洁很多。
2. **自动支持流式**：只要组件是 LCEL 兼容的，流式输出、异步、批量都是自动的，不用自己写。
3. **可组合**：一个 Runnable 可以嵌入另一个管道，搭积木一样。

示例就是这种风格：`prompt | model | outputParser`。它和普通写法的区别在于——**不是命令式地"调用"，而是声明式地"描述流程"**，框架来执行。

## 你实际用 LangChain 踩过什么坑？

我实际用下来有几个比较典型的坑，分享下：

1. **版本割裂**：LangChain 版本迭代快，旧代码经常一升级就废，网上教程很多是过时的。踩过之后我养成了习惯——**锁版本 + 只信官方文档**。
2. **过度抽象**：早期版本简单功能用 LangChain 写，代码比直接调 API 还绕。现在我的原则是**能直接调模型就直连，需要拼装组件才上 LangChain**。
3. **调试难**：框架帮你隐藏了细节，出问题不好定位。建议**每步都打日志**，看每个组件输入输出。
4. **跟 Agent 框架混用**：LangChain 的 Agent 和 LangGraph 的编排很容易搞混，我踩过用 Chain 当 Agent 用的坑——流程需要模型决策的地方用了写死的 Chain，结果业务复杂就绕不动。

一句话：LangChain 好用但别滥用，复杂编排上 LangGraph，简单直连就直连。
