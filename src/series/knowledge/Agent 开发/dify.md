# Dify 面试题

## Dify 是什么？为什么用 Dify 而不是直接写代码？

Dify 是个开源的 LLM 应用开发平台，核心卖点是**可视化编排**——把工作流、RAG、Agent 这些能力做成了拖拽的图形界面，不用自己从零搭。

我为什么要用它，说白了三点：

1. **快**：知识库、工作流、Agent 这些常见能力都是现成的，拖拖拽拽就搭起来了，比手写框架省很多事。
2. **内置了工程细节**：上下文管理、多模型切换、Prompt 调试、日志监控这些它都帮你做了，自己写的话这些全要自己造。
3. **可视化好跟人协作**：画出来的工作流给非技术的人看也看得懂，评审、交接都方便。

但我也清楚它的边界——**灵活度不如直接用代码写**，复杂逻辑、自定义编排还是会受限于平台能提供的节点。

---

## Dify 的工作流（Workflow）和 Agent 模式有什么区别？

这俩是 Dify 里最常见的两种编排方式，区别在**控制权归谁**：

1. **工作流（Workflow）**：流程是**写死的**，节点怎么连、每一步干什么都是你事先定好的，模型只在节点内部做有限的事。好处是稳定、可预期、好排查，适合业务逻辑清晰的固定流程，比如审批流、RAG 问答。
2. **Agent 模式**：给模型一个目标，让它**自己决定调什么工具、走什么步骤**，是自主决策的。适合开放任务，比如"帮我把这个需求拆了并给出方案"，但结果不稳定。

我的经验是：**能用工作流写死的就用工作流**，真需要发散探索的才交给 Agent。这样既稳又能保证关键路径不出错。

## Dify Agent 节点怎么编排工具调用？和直接调 LLM 的区别？

Agent 节点里，工具调用的逻辑是这样的：

1. 给 Agent 绑一组工具，每个工具都有 name + description 说明它干嘛、参数怎么填。
2. Agent 根据用户意图，从这组工具里挑合适的，输出结构化的调用参数（JSON）。
3. Dify 解析参数、执行对应工具，把结果返回给 Agent，Agent 再决定下一步——就是标准的 Function Calling 循环。

和直接调 LLM 的区别，我理解主要是：

- **直接调 LLM**：所有调用逻辑、循环、上下文管理都得自己写代码，模型只是"被调一下"。
- **Dify Agent 节点**：这个"工具选择 → 执行 → 观察 → 再决策"的循环平台替你管了，你只要把工具注册好，把 Prompt 配好就行。

所以用 Dify 搭 Agent，核心工作量从"写循环"变成了"**把工具定义清楚 + 把 Prompt 调好**"。

## Dify 的知识库 RAG 是怎么做的？流程是怎样的？

Dify 的知识库走的是标准 RAG 流程，我拆成两条线说：

**入库**：上传文档（PDF/Word/Markdown）→ 自动解析提取文本 → 智能分块 → Embedding 向量化 → 存进向量数据库。

**查询**：用户提问 → 问题也向量化 → 检索最相关的片段 → 拼到 Prompt 里 → 调 LLM 生成带引用的答案。

我实际用下来，有三个地方最容易影响效果，值得注意：

1. **分块大小**：太大检索不准，太小丢上下文，一般 500~1000 字符比较合适。
2. **检索方式**：纯语义对专有名词/编号不友好，纯关键词对同义词不友好，所以 Dify 默认推荐混合检索。
3. **引用溯源**：一定要让回答带出处，这样用户能核，也方便查幻觉。

## 为什么推荐混合检索而不是只用一种？

因为单一检索都有明显短板，我在实际项目里被坑过：

1. **纯语义检索（向量相似度）**：理解意图好，但专有名词、编号、精确术语容易查不准——比如产品型号、订单号这种，向量空间里它可能以为你问的是别的东西。
2. **纯关键词检索（BM25）**：精确词匹配好，但同义词、换个说法就废了，语义理解基本为零。

混合检索就是两者结合、加权排序：**语义检索兜住"意图理解"，关键词检索兜住"精确词汇"**。这样两边短板互补，召回和准确率都能上来。

一句话：这不是炫技，是实际测出来单用哪一种都会漏，合起来才稳。

## 文档分块大小怎么选？分块要注意什么？

分块这事没有标准答案，但有几个原则我总结出来了：

1. **大小要权衡**：太小→信息碎片化，一段话被切成两半，检索时缺上下文；太大→检索不精确，噪音多，还费 token。
2. **常用起点**：500~1000 字符比较常见，然后**拿你的真实问题去测**，看召回准不准，再调。
3. **块与块之间要重叠**：一般 10%~20%，避免刚好把关键句切到边界上。
4. **按内容类型调**：代码类可以稍大，说明文档可以稍小；有标题层级的话尽量按章节边界切，别硬切。

核心就是：**分块的目标是让"每个块能独立回答问题"**，而不是机械地按字数切。
