# Dify 面试题

## Dify 是什么？为什么用 Dify 而不是直接写代码？

**锚点**：`开源 LLM 应用平台：可视化编排现成能力，快但不灵活`

1. **快**：知识库、工作流、Agent 都是现成的，拖拽就搭起来，比手写框架省事
2. **内置工程细节**：上下文管理、多模型切换、Prompt 调试、日志监控都做好了，自己写全要造
3. **可视化好协作**：工作流画出来非技术的人看得懂，评审、交接方便
4. **边界**：灵活度不如直接用代码写，复杂逻辑、自定义编排受限于平台节点

## Dify 的工作流（Workflow）和 Agent 模式有什么区别？

**锚点**：`区别在控制权：工作流写死，Agent 自主`

1. **工作流（Workflow）**：流程写死，节点怎么连、每步干什么事先定好，模型只在节点内做有限的事——稳定、可预期、好排查，适合审批流、RAG 问答
2. **Agent 模式**：给目标让模型自己决定调什么工具、走什么步骤——适合开放任务（"帮我拆需求并给方案"），但结果不稳定
3. **经验**：能用工作流写死的就用工作流，真需要发散探索才交给 Agent，关键路径不出错

## Dify Agent 节点怎么编排工具调用？和直接调 LLM 的区别？

**锚点**：`平台替你管"选工具→执行→观察→再决策"循环，你只管工具定义和 Prompt`

1. **编排逻辑**：给 Agent 绑一组工具（name + description）→ Agent 按意图挑工具输出 JSON 参数 → Dify 执行返回结果 → Agent 再决策，标准 Function Calling 循环
2. **和直接调 LLM 的区别**：
   - 直接调：调用逻辑、循环、上下文管理全自己写
   - Dify Agent 节点：循环平台管了，你只要注册工具、配好 Prompt
3. **核心工作量变化**：从"写循环"变成"把工具定义清楚 + 把 Prompt 调好"

## Dify 的知识库 RAG 是怎么做的？流程是怎样的？

**锚点**：`入库：上传→解析→分块→向量化；查询：向量化→检索→拼 Prompt→生成`

1. **入库**：上传文档（PDF/Word/Markdown）→ 自动解析提取文本 → 智能分块 → Embedding 向量化 → 存向量数据库
2. **查询**：用户提问 → 问题向量化 → 检索相关片段 → 拼到 Prompt → LLM 生成带引用答案
3. **三个影响效果的点**：
   - 分块大小：太大检索不准、太小丢上下文，一般 500~1000 字符
   - 检索方式：纯语义对专有名词不友好、纯关键词对同义词不友好，Dify 默认推荐混合检索
   - 引用溯源：答案必须带出处，用户能核、方便查幻觉

## 为什么推荐混合检索而不是只用一种？

**锚点**：`语义兜意图、关键词兜精确词，互补才稳`

1. **纯语义检索（向量相似度）**：理解意图好，但专有名词、编号、精确术语查不准——产品型号、订单号可能被当成别的东西
2. **纯关键词检索（BM25）**：精确词匹配好，但同义词、换说法就废，语义理解基本为零
3. **混合检索**：两者结合、加权排序——语义兜住"意图理解"，关键词兜住"精确词汇"，召回和准确率都上来

一句话：这不是炫技，实际测出来单用哪一种都会漏，合起来才稳。

## 文档分块大小怎么选？分块要注意什么？

**锚点**：`500~1000 字符起步，块间重叠 10~20%，目标是每块能独立回答问题`

1. **大小权衡**：太小→碎片化丢上下文；太大→检索不精确、噪音多、费 token
2. **常用起点**：500~1000 字符，拿真实问题去测召回准不准再调
3. **块间重叠**：一般 10%~20%，避免关键句切到边界
4. **按内容类型调**：代码类稍大、说明文档稍小；有标题层级按章节边界切，别硬切

核心：**分块的目标是让"每个块能独立回答问题"，不是机械按字数切。**
