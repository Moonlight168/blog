# MCP 面试题

## 你平时用过哪些 MCP Server？有没有自己动手写过？

**锚点**：`用过三类（文件/Git、数据库、办公搜索）+ 自己写过：SDK 起 server 注册工具`

1. **用过（三类）**：
   - 文件/Git 类：官方 starter，把本地文件、仓库操作暴露给 Claude Code，读代码改文件方便
   - 数据库类：PostgreSQL/MySQL 的 MCP server，查表结构、跑查询，排障顺手
   - 办公/搜索类：Notion、飞书、Playwright 浏览器操作、搜索，生态现成接上就能用
2. **自己写（没那么玄乎）**：
   - 用官方 SDK（Python 的 fastmcp 或 TS 的 @modelcontextprotocol/sdk）起 server 注册工具
   - 每个工具 = 名字 + description + 输入 JSON Schema + 处理函数，把内部 API 或数据库查询包进去
   - 配置好 endpoint 告诉客户端（如 Claude Code 的 .mcp.json）就能直接调
3. **体验**：写一次 server，Claude Code、Cursor、自家 Agent 都能用，不用每家写一套适配

## 如果让你从零设计一个 MCP Server，你会怎么设计？

**锚点**：`先定边界 → 抠描述质量 → 管安全运行 → 可观测`

1. **先想清楚暴露什么**：频率高、Agent 能自主调用的才做成工具；低频或高风险操作（删数据、转账）宁可留给人
2. **工具定义质量优先**：name、description、输入 Schema 写清楚；description 说明何时用、参数怎么填——直接决定模型选得对不对
3. **传输和鉴权**：本地开发用 stdio，远程走 Streamable HTTP；鉴权、限流、审计在 server 层统一做，敏感凭据走环境变量/密钥管理
4. **错误和超时**：工具调用设超时；错误信息写清原因，让 Agent 自我修正而不是瞎猜
5. **可观测**：记调用日志（谁调的、参数、耗时、结果），出问题沿日志排查模型为什么跑偏

一句话：**设计重点不在协议本身，而在"工具边界 + 描述质量 + 安全兜底"三件事。**

## MCP 现在这么火，你觉得它有哪些局限？什么场景其实不该硬上 MCP？

**锚点**：`协议只解决"怎么接"，不解决"接得好不好"`

1. **不管工具质量**：描述写不清楚，接上 MCP 该跑偏还是跑偏
2. **本地开发有摩擦**：每个 server 独立进程，装多了就一堆常驻进程、端口、配置；轻量场景（一两个 API）直接 Function Calling 更省事
3. **远程有信任问题**：让 Agent 连远程 server 等于交出部分执行权，鉴权、数据边界得自己把关；生态出过恶意 MCP 投毒案例，接入前做安全评估
4. **性能开销**：每次调用多一层网络/进程往返，延迟敏感场景要掂量

判断：**跨系统、要复用的工具接 MCP 很值；单应用内只调一两个内部函数，直接写代码更简单。** MCP 是工具接入的"统一插头"，不是万能方案。
