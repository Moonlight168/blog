## 项目概述

OISG（Oil-quality Inspection Smart Guardian）是面向电力行业的变压器绝缘油试验数据分析平台。系统对绝缘油离线试验数据进行**规范性审核**与**异常预警**，并基于 **Dify + Spring AI** 构建智能问答助手，让业务人员通过自然语言即可完成数据查询、报告生成等操作。

**技术栈：** Spring Boot 3、Spring Security、JWT、MyBatis-Plus、达梦 DM8、Dify、Spring AI、Quartz、Apache POI、MinIO

## 面试问答

### Dify 在项目中是如何应用的？

**回答：** Dify 作为 LLM 应用编排平台，承担**工作流编排**与**知识库管理**两大职责：

1. **工作流编排**：在 Dify 中编排绝缘油智能问答助手的完整业务流
2. **意图分类**：使用 Dify 的 LLM 节点对用户输入进行意图识别，输出意图字段用于路由分发
3. **Agent 节点**：通过工具调用协议对接后端业务工具（设备查询、离线/在线数据、报告生成）
4. **知识库管理**：维护电力行业标准文档，实现 RAG 检索增强

---

### Dify 工作流的核心架构是怎样的？

**回答：** Dify 工作流采用「**意图分类 → 条件路由 → Agent 调用 → 参数提取 → 结果输出**」的多段式架构。

**核心节点（业务相关）：**

| 节点 | 作用 |
| --- | --- |
| **开始** | 接收用户输入 |
| **LLM 意图分类** | 识别用户意图，作为路由依据 |
| **条件分支** | 根据意图路由到不同处理路径 |
| **Agent 节点** | 调用后端业务工具（设备 / 数据 / 报告） |
| **参数提取器** | 抽取查询所需的关键参数 |
| **LLM 闲聊 / 知识库检索** | 非业务意图走闲聊 + 知识库 |
| **直接输出** | 部分场景直接返回结果 |

---

### Dify 中的意图是如何分类的？

**回答：** 通过 LLM 节点对用户输入进行意图分类，输出意图字段，作为后续路由的依据。

**典型业务意图：**

| 意图 | 处理路径 | 说明 |
| --- | --- | --- |
| 通用对话 | 知识库检索 → LLM 闲聊 | 闲聊问答 |
| 巡检推荐 | Agent → 直接输出 | 巡检建议 |
| 离线 / 在线数据 | 设备确认 → 参数提取 → 数据查询 Agent | 业务数据查询 |
| 报告生成 | 设备确认 → 参数提取 → 报告生成 Agent | 自动报告 |

---

### Dify + Spring AI 是如何集成的？

**回答：** Dify 作为前端编排与 LLM 调度，Spring AI 作为后端业务能力的工具暴露层，两者通过 **MCP（Model Context Protocol）** 协议通信。

**集成步骤：**

1. **后端**：使用 Spring AI 的 `@Tool` 注解将业务方法注册为 MCP 工具
2. **协议暴露**：通过 Spring AI 的 MCP 模块发布工具到 MCP Server
3. **Dify 配置**：在 Dify Agent 节点中配置 MCP Server 地址，自动发现并调用工具
4. **调用流程**：
   ```
   用户提问 → Dify Agent → MCP 协议 → Spring AI → 业务方法 → 返回结果
   ```

---

### Spring AI 的 MCP 服务是如何实现的？

**回答：** 基于 Spring AI 的 MCP 模块，使用注解驱动方式将业务方法暴露为工具。

**核心实现：**

- **工具注册**：使用 `@Tool` 注解标注业务方法
- **工具集暴露**：使用 `@ToolProvider` 或 `MethodToolCallback` 暴露工具集
- **协议发布**：通过 `spring-ai-starter-mcp-server-webmvc`（或 webflux）模块发布到 MCP Server
- **传输方式**：支持 stdio / SSE / HTTP 等传输协议

---

### MCP 工具集包含哪些？各自的作用是什么？

**回答：** 项目通过 MCP 协议注册了多类业务工具：

| 工具 | 作用 |
| --- | --- |
| **设备查询工具** | 设备信息查询（变电站、相别、设备号） |
| **离线试验数据工具** | 离线试验数据查询 |
| **在线监测数据工具** | 在线监测数据查询 |
| **报告生成工具** | 报告模板填充与生成 |
| **知识库检索工具** | 知识库检索（RAG） |

**追问：为什么选择 MCP 而不是 Function Calling？**

**回答：** MCP 提供标准化的工具描述与发现机制，工具可被多个 Agent 复用；Function Calling 是模型级别的紧耦合，灵活性较差。

---

### 多轮对话中如何管理设备确认状态？

**回答：** 工作流通过状态机控制多轮对话：

- **`init` 状态**：首次进入业务查询时，要求用户确认设备信息
- **`confirmed` 状态**：设备已确认，可直接查询数据 / 生成报告
- **状态转移**：当用户切换设备时，状态机会重置回 `init`，重新要求确认

Dify 通过变量赋值 + 条件分支实现状态机的流转，状态保存在会话上下文中。

---

### 离线数据规范性审核是如何实现的？

**回答：** 基于离线试验数据与在线气体监测数据实现指标对比，按**偏差分级策略**完成审核。

**核心逻辑：**

1. **规则配置**：维护对比规则的误差阈值
2. **数据比对**：将离线数据与在线监测数据进行指标对比
3. **偏差分级**：根据偏差程度分为正常 / 警告 / 异常
4. **预警触发**：识别数据缺失与超标异常，触发预警
5. **消息推送**：集成企业微信 / 短信告警

---

### 报告生成功能是如何实现的？

**回答：** 基于 **Apache POI** 实现 Word 模板的占位符填充，结合 **MinIO** 完成报告文件的存储。

**实现流程：**

1. 业务人员通过 Dify 助手触发报告生成
2. Agent 调用报告工具获取数据
3. 使用 Apache POI 加载 Word 模板，替换占位符
4. 生成的报告文件上传到 MinIO
5. 返回报告下载链接给用户

**追问：模板是如何管理的？**

**回答：** 支持模板的上传与管理，模板存储在 MinIO 中，数据库维护模板元信息（模板 ID、名称、占位符定义等）。

---

### 知识库是如何接入的？

**回答：** 使用 Dify 内置的知识库能力：

1. **文档导入**：将电力行业标准、规范文档导入 Dify 知识库
2. **文档解析**：Dify 自动解析文档并进行向量化
3. **检索增强**：当用户提问非业务问题时，先检索知识库，再结合 LLM 生成答案
4. **工具暴露**：通过 MCP 工具暴露知识库检索能力给 Agent

---

### 消息推送是如何集成的？

**回答：** 集成企业微信 / 短信告警平台，实现异常告警推送。

**应用场景：**

- 离线数据规范性审核不通过 → 推送企业微信消息给责任人
- 阈值预警触发 → 短信通知值班人员
- 报告生成完成 → 推送消息并附带下载链接

### 项目的技术架构是怎样的？

**回答：** 项目采用 **Maven 多模块架构**，基于 **Spring Boot 3** 构建，按"启动 / 框架 / 业务 / 集成"分层组织：

- **启动层**：Web 启动入口，统一加载配置

- **集成层**：定时任务、外部系统对接、消息推送等集成模块

### 项目中遇到什么技术难点？如何解决的？

**回答要点：** 结合项目实际实现，列举 2-3 个具体技术难点及解决方案。

**示例 1：Dify 工作流多轮对话状态管理**

**问题：** 多轮对话中用户会切换设备，需要重新确认设备信息才能查询数据。

**解决：** 引入状态机：
   - **`init` 状态**：首次进入业务查询时，要求用户确认设备信息
   - **`confirmed` 状态**：设备已确认，可直接查询数据
   - **状态转移**：通过 Dify 条件分支 + 变量赋值实现

**示例 2：Spring AI 工具注解与业务逻辑解耦**

**问题：** 工具需要在不污染业务代码的前提下暴露给 LLM 调用。

**解决：** 使用 Spring AI 的 `@Tool` / `@ToolParam` 注解：
   - 业务方法本身保持纯净（POJO + Service）
   - 通过工具回调装饰业务方法，添加工具描述与参数说明
   - 业务代码与工具描述解耦，便于维护与扩展

**示例 3：离线数据规范性审核的性能优化**

**问题：** 大量离线试验数据需要与在线数据进行比对，规则计算复杂，性能瓶颈明显。

**解决：**
   - **批处理**：将数据按设备分组
   - **规则预编译**：审核规则在启动时编译为表达式，避免重复解析
   - **并行计算**：使用线程池并行处理不同设备的数据
   - **异步推送**：预警消息通过异步推送，不阻塞主流程

### Spring AI MCP 与传统 Function Calling 的区别是什么？

**回答：**

| 维度 | Spring AI MCP | Function Calling |
| --- | --- | --- |
| **标准化** | 标准协议，跨模型/平台 | 厂商特定（OpenAI、Anthropic 等各自实现） |
| **工具复用** | 工具一次开发，多 Agent 复用 | 每个 Agent 需单独定义工具 |
| **传输方式** | stdio / SSE / HTTP | HTTP（模型厂商 API） |
| **可维护性** | 工具与业务解耦 | 工具定义常与业务代码耦合 |
| **生态** | 标准化协议，逐步成为行业标准 | 各厂商独立演进 |

MCP 更适合**企业级、多 Agent 协作**的场景；Function Calling 适合**单一模型、快速集成**的场景。
