## Kafka 是什么？

**锚点**：`分布式流平台：发布-订阅消息队列，高吞吐 + 分布式架构`

Kafka 是一个分布式流平台，主要用于高吞吐量的消息传递、日志收集、事件流处理等应用场景。它本质上是一个发布-订阅模式的消息队列，但具有更高的吞吐量和分布式架构。

## Kafka 的特点？

**锚点**：`高吞吐、分布式、持久化、分区有序、消费组、可扩展`

1. **高吞吐量**：能处理非常高的消息吞吐量，适合大规模数据流实时处理
2. **分布式架构**：多节点集群，横向扩展，高可用
3. **持久化**：消息默认持久化到磁盘，日志多副本备份，数据不丢
4. **消息顺序性**：保证每个分区内消息的顺序性
5. **灵活消费模式**：消费者组共同消费一个主题，也可独立消费
6. **高可扩展性**：扩展分区增加负载能力，并行消费提高吞吐

## Kafka 的架构组件有哪些，各自的职责是什么？

**锚点**：`生产-存储-消费三主线 + 协调（ZK）+ 扩展（Streams/Connect）`

1. **Producer（生产者）**：发消息到 Topic，可选分区或自动选择；支持负载均衡、异步批量发送
2. **Consumer（消费者）**：订阅 Topic 消费消息；组内并行、每条消息只被组内一个消费者处理、可从指定偏移量开始读
3. **Broker（代理）**：集群节点，管理分区存储、持久化、副本，处理生产/消费请求
4. **Topic（主题）**：消息的逻辑类别，可多分区，按主题路由组织
5. **Partition（分区）**：主题的分片，每个分区是日志文件，分区内有序，支持水平扩展
6. **Zookeeper**：协调服务，管理元数据、Broker 注册、故障检测、Leader 选举（Kafka 计划逐步去除该依赖）
7. **Kafka Streams**：流处理库，实时数据流处理，提供内存存储和状态管理
8. **Kafka Connect**：外部系统集成框架，预构建连接器，支持批量和增量数据处理

## Kafka 组件之间的关系？

**锚点**：`生产者写分区、消费者读分区、Broker 存储、ZK 协调、Streams/Connect 扩展`

1. **生产者**将消息写入**主题**的**分区**
2. **消费者**从**主题**的**分区**中读取消息
3. **Broker**存储和管理消息，并通过**Zookeeper**协调集群
4. **Kafka Streams**和**Kafka Connect**分别用于流处理和数据集成

## Kafka 的原理？

**锚点**：`分区并行 + 顺序写磁盘 + 副本 ISR 高可用 + 消费组可扩展`

Kafka 本质是基于发布订阅模型的分布式消息系统，核心设计：

1. 通过 Topic 的 **Partition** 实现并行
2. 通过**顺序写磁盘**的日志结构保证高吞吐
3. 通过**副本和 ISR 机制**保证高可用
4. 消费者通过 **Consumer Group** 实现可扩展消费

## Kafka 为什么能支持高吞吐？

**锚点**：`顺序写 + 批量压缩 + 零拷贝 + 分区并行`

1. **顺序写入**：追加写磁盘，充分利用顺序 IO（比随机写快几个数量级）；配合 OS 页缓存，写入即返回
2. **批量 + 压缩**：生产者批量攒消息发送、消费者批量拉取；支持 GZIP/Snappy/LZ4 压缩，减少网络和存储
3. **零拷贝**：消费端 `sendfile()`，数据从磁盘页缓存直接 DMA 到网卡，不经过用户态——省 2 次 CPU 拷贝和 2 次上下文切换
   - 传统路径：磁盘 → 内核 → 用户态 → Socket 内核 → 网卡（4 次拷贝）
   - 零拷贝：磁盘 → 内核页缓存 → 网卡（只走 DMA）
4. **分区并行**：一个 Topic 拆多个 Partition，生产消费并行处理，横向扩展

## Kafka 中消费者组（Consumer Group）的作用是什么？

**锚点**：`组内负载均衡，组间广播`

1. **分区独占消费**：同一组内一个分区最多只被一个消费者消费；组内消费者数 > 分区数时，多出的闲置
2. **负载均衡 + 水平扩展**：多个消费者各负责不同分区并行消费，吞吐随消费者数线性增长，上限 = 分区数
3. **Rebalance（重平衡）**：消费者加入/退出组时自动重新分配分区，保证高可用
4. **组间独立（发布/订阅语义）**：不同组各自独立消费同一 Topic，维护各自 Offset，互不影响
5. **Offset 管理**：每组独立记录消费进度，重启后从上次位置继续

## Kafka 消费者组为什么分区独占消费？

**锚点**：`保顺序 + 简化 Offset + 重平衡前提——用利用率换一致性和扩展性`

1. **消息顺序保证**：分区内严格有序，多消费者同时消费同一分区会破坏顺序
2. **Offset 管理简化**：一个分区只有一个消费者，提交逻辑清晰，不会冲突
3. **Rebalance 前提**：分区与消费者的独占映射是重平衡机制的基础，保证故障转移时分配确定性
4. **设计取舍**：主动牺牲利用率换顺序和一致性；扩展吞吐靠增加分区数而非共享分区
5. **热备冗余**：消费者数 > 分区数时，多出的空闲消费者作热备（Hot Standby），有人挂掉立刻顶上
