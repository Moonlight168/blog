## ⭐ Java 中的多线程实现方式有哪些？

**锚点**：`五种：Thread / Runnable / Callable / ExecutorService / ForkJoinPool`

1. **继承 Thread**：重写 `run()`，`start()` 启动——简单但不能再继承其他类
2. **实现 Runnable**：最常用，无返回值，避免单继承限制
3. **Callable + Future**：有返回值、可抛异常，通过线程池 `submit()` 提交，`future.get()` 取结果
4. **ExecutorService 线程池**：实际项目必用，避免频繁创建销毁线程
5. **ForkJoinPool**：并行计算专用

## Java线程和操作系统线程的关系是什么？

**锚点**：`早期绿色线程（JVM 管），JDK 1.4+ 1:1 映射到 OS 线程`

1. **早期模型（JDK 1.1-1.3）**：绿色线程，JVM 管理，无法利用多核
2. **现代模型（JDK 1.4+）**：1:1 映射，每个 Java 线程直接映射 OS 线程
3. **优点**：充分利用多核、OS 级别调度；**缺点**：创建开销大、受 OS 限制

## 用户线程和系统线程的区别是什么？

**锚点**：`用户线程用户态管理开销小但阻塞影响大；系统线程内核调度可多核`

| 特性 | 用户线程 | 系统线程 |
|------|----------|----------|
| 管理 | 用户程序管理 | 操作系统内核管理 |
| 调度 | 用户态线程库 | 内核调度器 |
| 开销 | 创建切换开销小 | 开销大 |
| 多核利用 | 无法利用 | 可充分利用 |
| 阻塞影响 | 一个阻塞可能阻塞整个进程 | 不影响其他线程 |

Java 采用 1:1 映射模型，属于系统线程范畴。

## 什么是线程安全？如何实现？

**锚点**：`并发访问共享数据不错乱；四手段：锁/安全类/原子类/不共享`

1. **同步（锁机制）**：`synchronized`、`ReentrantLock`、`ReentrantReadWriteLock`
2. **线程安全类**：`CopyOnWriteArrayList`、`ConcurrentHashMap`、`BlockingQueue`
3. **原子类（无锁 CAS）**：`AtomicInteger`、`AtomicLong`、`AtomicReference`
4. **不共享数据**：局部变量、`ThreadLocal`（每线程独立副本）

## 什么是锁？为什么需要锁？

**锚点**：`控制共享资源访问，确保同一时刻单线程访问`

1. 防止竞态条件，避免多线程同时读写结果异常
2. 保证线程安全，确保数据一致性与可见性
3. 协调线程访问顺序

## JMM（Java内存模型）有了解吗？

**锚点**：`三性：可见性 / 有序性 / 原子性；主内存 + 工作内存模型`

1. **可见性**：一个线程修改别的线程能否看到 → `volatile`、`synchronized`
2. **有序性**：指令是否被重排序 → `volatile`、`synchronized` 禁止重排序
3. **原子性**：操作是否不可分割 → `synchronized`、`Lock`
4. **核心模型**：变量存主内存，每线程有自己的工作内存副本

## Java 中的主要锁机制有哪些？

**锚点**：`synchronized / ReentrantLock / 读写锁 / StampedLock / Semaphore / 原子类`

1. **synchronized**：内置锁，可重入、互斥、自动释放
2. **ReentrantLock**：可中断、可公平/非公平、支持 `tryLock()`
3. **ReentrantReadWriteLock**：读写分离，读多写少场景
4. **StampedLock**（JDK8）：支持乐观读，性能更高
5. **Semaphore**：信号量，控制同时访问的线程数量
6. **原子类**：基于 CAS 无锁实现

## `synchronized` 的使用方式有哪些？

**锚点**：`实例方法锁 this / 静态方法锁 Class / 代码块指定锁对象`

1. 修饰**实例方法**：锁住当前实例对象 `this`
2. 修饰**静态方法**：锁住类对象 `Class`
3. 修饰**代码块**：指定锁对象，更灵活

## 什么是可重入锁？

**锚点**：`同一线程外层拿到锁，内层可再次获取不阻塞`

1. 避免死锁：同一线程可重复获取已拥有的锁
2. 支持递归调用

常见实现：`synchronized`、`ReentrantLock`。

## `synchronized` 是如何实现的？

**锚点**：`对象头 Mark Word 记录锁状态 + 锁升级 + Monitor`

1. **对象头存储锁信息**：Mark Word 记录锁标志位、线程 ID
2. **锁升级机制**：偏向锁 → 轻量级锁（CAS 自旋）→ 重量级锁（Monitor）
3. **字节码层面**：`monitorenter` 进入同步块，`monitorexit` 退出

## `ReentrantLock`的底层如何实现的？

**锚点**：`基于 AQS：state 记录持有次数 + 等待队列；公平/非公平`

1. **AQS 基础**：`state` 变量记录锁获取次数，维护线程等待队列
2. **重入实现**：state=0 无锁，state>0 持有，每次重入 +1
3. **公平性**：公平锁按请求顺序；非公平锁直接 CAS 抢
4. **与 synchronized 区别**：显式 lock/unlock、可选择公平、多个 Condition、支持中断和超时

## `ReentrantLock`与`synchronized`的区别是什么？

**锚点**：`显式/隐式、可中断/不可、tryLock、公平可选、多 Condition`

| 特性 | synchronized | ReentrantLock |
|------|-------------|----------------|
| 锁获取 | 隐式获取释放 | 显式 lock()/unlock() |
| 可中断性 | 不可中断 | 可中断 |
| 尝试锁 | 不支持 | 支持 tryLock() |
| 公平性 | 非公平 | 公平/非公平可选 |
| 条件变量 | 单一 wait/notify | 多个 Condition |

## 什么情况下选择`synchronized`或`ReentrantLock`？

**锚点**：`简单场景 synchronized，需高级特性（中断/超时/公平/多条件）用 ReentrantLock`

- **synchronized**：代码简单、不需要高级锁特性，优先可读性
- **ReentrantLock**：需要可中断锁、尝试锁、公平锁或多个条件变量

## 什么是读写锁？

**锚点**：`读读并行、写写/读写互斥——读多写少场景`

1. **读锁**：多个线程可同时持有，只要没有写锁
2. **写锁**：独占锁，持有写锁时其他线程无法读写

## 什么是公平锁和非公平锁？

**锚点**：`公平先到先得；非公平可插队（默认），吞吐更高`

- **公平锁**：线程按请求顺序获取锁，先到先得
- **非公平锁**：获取顺序不确定，可能后请求的先获得

`ReentrantLock` 默认非公平，`new ReentrantLock(true)` 指定公平。

## `StampedLock`是什么？

**锚点**：`JDK8 高性能锁：乐观读 / 悲观读 / 写锁，读多写少`

1. **乐观读**：不获取锁直接读取，性能最高
2. **悲观读**：类似传统读锁
3. **写锁**：独占锁

## 乐观锁的典型实现方式有哪些？

**锚点**：`版本号机制 / CAS`

1. **版本号机制**：每次修改递增版本号，更新时检查版本号一致
2. **CAS**：原子操作，比较内存值与预期值，相同才更新

## CAS是什么？底层原理是什么？

**锚点**：`无锁算法：V 内存值 / A 预期值 / B 新值，V==A 才更新为 B`

1. **三个操作数**：内存位置（V）、预期原值（A）、新值（B）
2. **底层**：CPU 原子指令（x86 的 `CMPXCHG`）；Java 通过 `Unsafe.compareAndSwap` 实现

## 乐观锁有哪些优缺点？

**锚点**：`无锁并发高、非阻塞；冲突重试耗 CPU、有 ABA 问题`

**优点**：无锁开销提高并发性能；非阻塞减少上下文切换；适合读多写少

**缺点**：冲突时重试消耗 CPU；不适合长事务（冲突概率大）；**ABA 问题**（用 `AtomicStampedReference` 解决）

## 什么是ABA问题？如何解决？

**锚点**：`A→B→A 后 CAS 误判未修改；AtomicStampedReference 加版本号`

**问题**：值从 A 变为 B 再变回 A，CAS 操作误认为值未修改。

**解决**：使用 `AtomicStampedReference`，每次修改增加版本号。

## 乐观锁和悲观锁的适用场景是什么？

**锚点**：`读多写少冲突少用乐观；写多冲突多用悲观`

| 场景 | 乐观锁 | 悲观锁 |
|------|--------|--------|
| 读写比例 | 读多写少 | 写多读少 |
| 冲突频率 | 冲突少 | 冲突多 |
| 典型实现 | CAS、版本号 | synchronized、ReentrantLock |

## 锁与原子类的区别是什么？

**锚点**：`锁阻塞保安全适合复杂操作；原子类 CAS 非阻塞适合简单操作`

- **锁**：通过阻塞线程保证线程安全，适合保护复杂操作
- **原子类**：基于 CAS 非阻塞，适合简单原子操作，性能更好

## 什么是锁的饥饿和公平性问题？

**锚点**：`饥饿 = 部分线程长期拿不到锁；公平锁解决但有性能开销`

- **锁饥饿**：某些线程长期无法获得锁，性能下降
- **公平性**：公平锁确保所有线程有机会获锁，但有性能开销

## 什么是 Condition 接口？

**锚点**：`替代 wait/notify：await + signal，一个 Lock 可关联多个 Condition`

用于替代传统 `wait()`/`notify()`，与 Lock 配合，每个 Lock 可关联多个 Condition 对象。

- 等待：`await()`、`await(long time, TimeUnit unit)`
- 唤醒：`signal()`、`signalAll()`

## ThreadLocal原理是什么？

**锚点**：`每线程一个 ThreadLocalMap：key 弱引用 ThreadLocal，value 强引用`

1. **存储结构**：每个 Thread 对象含 `ThreadLocalMap`，键为 ThreadLocal 实例，值为线程局部变量
2. **工作流程**：`set()`/`get()` 操作当前线程的 ThreadLocalMap
3. **内存管理**：Entry 用弱引用指向 ThreadLocal，避免泄漏

**注意**：使用后调 `remove()` 清理，防止内存泄漏。

## 两个线程同时操作同一条数据，如何保证数据安全？

**锚点**：`单实例本地锁；分布式必须外部锁（DB 行锁/乐观锁/Redis、ZK 分布式锁）`

- **单实例服务**：本地锁即可（`synchronized`、`ReentrantLock`），线程都在同一 JVM
- **多实例/分布式**：必须外部锁——数据库行锁（`SELECT ... FOR UPDATE`）、乐观锁（版本号）、分布式锁（Redis / Zookeeper）
- **核心**：是否需要分布式锁取决于是否分布式场景，本地锁只能单实例生效

## 什么是线程的虚假唤醒？为什么使用 while 而不是 if？

**锚点**：`没收到 notify 也可能醒；while 苏醒后重查条件`

**虚假唤醒**：线程在没有收到 `notify()` 或条件真正满足的情况下从 `wait()` 意外苏醒，Java 规范明确允许。

**为什么用 while**：`if` 只查一次条件，虚假唤醒会直接执行导致错误；`while` 每次苏醒重新检查，确保条件真正满足。

## 为什么在多线程中不建议使用 `static` 共享变量？

**锚点**：`数据竞争 + 可见性 + 破坏封装；替代：原子类/锁/并发容器`

1. **线程安全**：static 类级别，多线程修改导致数据竞争、状态错乱
2. **可见性**：CPU 缓存导致不同线程读到旧值
3. **可维护性**：共享状态破坏封装、增加耦合

**替代**：`AtomicInteger`、synchronized 代码块、`ConcurrentHashMap`。

## 如何实现无锁的线程安全单例？

**锚点**：`枚举（推荐）/ 静态内部类 / 饿汉式——都靠 JVM 类加载保证线程安全`

1. **枚举单例（推荐）**：JVM 保证只加载一次，天生安全，防反序列化、防反射

```java
public enum Singleton {
    INSTANCE;
    public void doSomething() { }
}
```

2. **静态内部类**：依赖 JVM 类加载机制，懒加载

```java
public class Singleton {
    private Singleton() {}
    private static class Holder {
        private static final Singleton INSTANCE = new Singleton();
    }
    public static Singleton getInstance() { return Holder.INSTANCE; }
}
```

3. **饿汉式**：类加载时就创建，JVM 保证安全

## 线程池任务提交流程？

**锚点**：`核心 → 队列 → 非核心 → 拒绝`

1. 线程数 < corePoolSize → **新建线程**
2. 线程数 ≥ corePoolSize → 进**工作队列**
3. 队列满 + 线程数 < maxPoolSize → 新建非核心线程
4. 队列满 + 线程数 = maxPoolSize → **拒绝策略**

## 线程池核心参数和任务提交流程？

**锚点**：`六参数：core / max / keepAlive / workQueue / threadFactory / 拒绝策略`

| 参数 | 含义 |
|---|---|
| corePoolSize | 核心线程数 |
| maxPoolSize | 最大线程数 |
| keepAliveTime | 非核心线程空闲存活时间 |
| workQueue | 阻塞队列（任务缓冲区） |
| threadFactory | 线程工厂 |
| rejectedExecutionHandler | 拒绝策略 |

**提交流程**：线程数 < corePoolSize → 新建核心线程；≥ core 进队列；队列满 + 未到 max 新建非核心；队列满 + 到 max → 拒绝策略

**四种拒绝策略**：AbortPolicy 抛异常（默认）；CallerRunsPolicy 退回调用者执行；DiscardPolicy 静默丢弃；DiscardOldestPolicy 丢队列头部旧任务

## 线程池核心参数有哪些？核心线程和最大线程区别？

**锚点**：`核心线程常驻不回收；最大线程里的非核心空闲超时即销毁`

| 参数 | 作用 |
|------|------|
| corePoolSize | 核心线程，一直存活（空闲也不回收） |
| maxPoolSize | 最大线程数，核心不够 + 队列满才扩 |
| keepAliveTime | 非核心线程空闲多久回收 |
| workQueue | 阻塞队列，核心忙时任务先进队列 |
| threadFactory | 线程工厂，自定义线程名 |
| rejectedExecutionHandler | 队列满 + 线程到最大 → 拒绝策略 |

- **核心 vs 最大**：核心线程不回收（除非 `allowCoreThreadTimeOut`），最大线程里的非核心空闲超时销毁

## synchronized 锁升级过程是怎样的？

**锚点**：`偏向锁 → 轻量级锁 → 重量级锁（不可逆）`

- **偏向锁**（无竞争）：同一线程反复获取，对象头记录线程 ID，连 CAS 都不需要；另一线程竞争时撤销偏向
- **轻量级锁**（竞争不激烈）：CAS 自旋抢锁，适合锁持有时间短；自旋失败次数多 → 膨胀
- **重量级锁**（竞争激烈）：自旋耗 CPU，膨胀为 OS mutex，线程阻塞进等待队列，切换成本高
- **设计思想**：大多数锁生命周期无竞争，轻量手段覆盖常见场景，竞争激烈才走内核态

## ThreadLocal 是什么？有哪些使用场景？内存泄漏是怎么造成的？

**锚点**：`线程本地变量；key 弱引用 value 强引用；线程池长期存活 + 不 remove = 泄漏`

**是什么**：线程本地变量，每线程独立副本，线程间隔离。实现：每线程内部一个 ThreadLocalMap，key 是 ThreadLocal 的**弱引用**，value 是变量值的**强引用**。

**使用场景**：保存当前请求 userId；Spring 事务管理器存 DB 连接；SimpleDateFormat 隔离（线程不安全）。

**内存泄漏原因**：

1. key 是弱引用，GC 可回收
2. key 被回收后 value 是强引用不回收，且**没有 key 再也访问不到**，成无法释放的垃圾
3. 线程池线程长期存活 → Entry 一直挂在线程的 ThreadLocalMap 里 → 泄漏

**防治**：用完后必须调 **`remove()`**。get()/set() 会顺带清理个别 key 为 null 的 Entry，但不保证全覆盖。
