## ⭐ Java 中的多线程实现方式有哪些？

* **Thread**：简单但受限（继承）
* **Runnable**：最常用，无返回值
* **Callable**：有返回值
* **ExecutorService**：实际项目必用
* **ForkJoinPool**：并行计算专用

**继承 `Thread`**

* **重写 `run()`，调用 `start()` 启动线程**
* 缺点：**不能再继承其他类**

```java
class MyThread extends Thread {
    public void run() {
        System.out.println("Thread running");
    }
}

new MyThread().start();
```

**实现 `Runnable`**

* **更灵活，可与线程分离**
* 推荐使用，因为 **避免单继承限制**

```java
class MyRunnable implements Runnable {
    public void run() {
        System.out.println("Runnable running");
    }
}

new Thread(new MyRunnable()).start();
```

---

**使用 `Callable` + `Future`**

* **有返回值**，可抛异常
* 通过线程池 `submit()` 提交任务

```java
class MyCallable implements Callable<String> {
    public String call() {
        return "Callable running";
    }
}

ExecutorService pool = Executors.newFixedThreadPool(1);
Future<String> future = pool.submit(new MyCallable());
System.out.println(future.get());
pool.shutdown();
```

**使用线程池 `ExecutorService`**

* **最佳生产实践**
* 避免频繁创建销毁线程

```java
ExecutorService pool = Executors.newFixedThreadPool(2);
pool.submit(() -> System.out.println("Thread pool running"));
pool.shutdown();
```

## Java线程和操作系统线程的关系是什么？

1. **早期模型（JDK 1.1-1.3）**：绿色线程，由JVM管理，无法利用多核CPU
2. **现代模型（JDK 1.4+）**：1:1映射，每个Java线程直接映射到操作系统线程

**优点**：充分利用多核CPU、操作系统级别调度
**缺点**：线程创建开销大、受操作系统限制

## 用户线程和系统线程的区别是什么？

**回答：**

| 特性 | 用户线程 | 系统线程 |
|------|----------|----------|
| 管理 | 用户程序管理 | 操作系统内核管理 |
| 调度 | 用户态线程库 | 内核调度器 |
| 开销 | 创建和切换开销小 | 开销大 |
| 多核利用 | 无法利用（纯用户线程） | 可充分利用 |
| 阻塞影响 | 一个阻塞可能导致整个进程阻塞 | 不影响其他线程 |

Java采用1:1映射模型，属于系统线程范畴。

## 什么是线程安全？如何实现？

线程安全指在多线程同时访问共享数据时，不会出现数据错误、结果不一致、状态混乱等问题。

**实现方式**：

1. **使用同步（锁机制）**：`synchronized`、`ReentrantLock`、`ReentrantReadWriteLock`
2. **使用线程安全的类**：`CopyOnWriteArrayList`、`ConcurrentHashMap`、`BlockingQueue`
3. **使用原子类（无锁CAS）**：`AtomicInteger`、`AtomicLong`、`AtomicReference`
4. **不共享数据**：局部变量、`ThreadLocal`（为每个线程提供独立副本）

## 什么是锁？为什么需要锁？

锁是多线程编程中的机制，用于控制对共享资源的访问，确保每次只有一个线程访问资源。

**为什么需要锁**：
1. 防止竞态条件，避免多线程同时读写导致结果异常
2. 保证线程安全，确保数据一致性与可见性
3. 协调线程访问顺序

## JMM（Java内存模型）有了解吗？

JMM规定了多线程之间变量如何可见、如何有序、如何避免冲突，是 Java 并发的基础规则。

1. **可见性**：一个线程修改，别的线程是否能看到 → `volatile`、`synchronized`
2. **有序性**：指令是否会被重排序 → `volatile`、`synchronized`禁止重排序
3. **原子性**：操作是否不可分割 → `synchronized`、`Lock`保证

**核心模型**：变量存在主内存，每个线程有自己的工作内存副本。

## Java 中的主要锁机制有哪些？

1. **synchronized**：内置锁，可重入、互斥、自动释放
2. **ReentrantLock**：可中断、可公平/非公平、支持`tryLock()`
3. **ReentrantReadWriteLock**：读写分离，适合读多写少场景
4. **StampedLock**：JDK8提供，支持乐观读，性能更高
5. **Semaphore**：信号量，控制同时访问资源的线程数量
6. **原子类**：基于CAS无锁实现，如`AtomicInteger`

## `synchronized` 的使用方式有哪些？

1. **修饰实例方法**：锁住当前实例对象`this`
2. **修饰静态方法**：锁住类对象`Class`
3. **修饰代码块**：指定锁对象，更灵活

## 什么是可重入锁？

可重入锁指同一个线程在外层方法获得锁后，可以在内层方法再次获得该锁而不会被阻塞。

**特点**：
1. 避免死锁：同一线程可重复获取已拥有的锁
2. 支持递归调用

**常见实现**：`synchronized`、`ReentrantLock`

## `synchronized` 是如何实现的？

`synchronized`通过对象头的Mark Word记录锁状态，通过锁升级机制提高性能，最终依赖JVM Monitor实现线程同步。

1. **对象头存储锁信息**：Mark Word记录锁标志位、线程ID
2. **锁升级机制**：偏向锁 → 轻量级锁（CAS自旋）→ 重量级锁（Monitor）
3. **字节码层面**：`monitorenter`进入同步块，`monitorexit`退出同步块

## `ReentrantLock`的底层如何实现的？

ReentrantLock基于AQS实现，是可重入的独占锁。

1. **AQS基础**：通过state变量记录锁获取次数，维护线程等待队列
2. **重入实现**：state=0表示无锁，state>0表示线程持有锁，每次重入state+1
3. **公平性**：公平锁按请求顺序获取，非公平锁直接尝试CAS获取

**与synchronized区别**
| 特性 | ReentrantLock | synchronized |
|------|---------------|--------------|
| 获取方式 | 显式`lock()`/`unlock()` | 隐式（代码块/方法） |
| 公平性 | 可选择 | 非公平 |
| 条件变量 | 多个 | 单个 |
| 中断响应 | 支持 | 不支持 |
| 超时机制 | 支持 | 不支持 |

## `ReentrantLock`与`synchronized`的区别是什么？

| 特性 | `synchronized` | `ReentrantLock` |
|------|---------------|-----------------|
| 锁获取方式 | 隐式获取和释放 | 显式调用`lock()`和`unlock()` |
| 可中断性 | 不可中断 | 可中断 |
| 尝试锁 | 不支持 | 支持`tryLock()` |
| 公平性 | 非公平 | 可选择公平或非公平 |
| 条件变量 | 单一`wait/notify` | 可创建多个`Condition` |

## 什么情况下选择`synchronized`或`ReentrantLock`？

- **选择`synchronized`**：代码简单，不需要高级锁特性，优先考虑可读性
- **选择`ReentrantLock`**：需要可中断锁、尝试锁、公平锁或多个条件变量

## 什么是读写锁？

读写锁允许多个线程同时读取，但写操作时只能单线程独占，适合读多写少的场景。

1. **读锁**：多个线程可同时持有，只要没有写锁
2. **写锁**：独占锁，持有写锁时其他线程无法读写

## 什么是公平锁和非公平锁？

- **公平锁**：线程按请求顺序获取锁，先到先得
- **非公平锁**：线程获取锁顺序不确定，可能后请求的先获得

`ReentrantLock`默认是非公平锁，可通过构造函数指定为公平锁：
```java
Lock fairLock = new ReentrantLock(true); // 公平锁
```

## `StampedLock`是什么？

`StampedLock`是JDK8引入的高性能锁，适合读多写少场景。

1. **乐观读**：不获取锁直接读取，性能最高
2. **悲观读**：类似传统读锁
3. **写锁**：独占锁

## 乐观锁的典型实现方式有哪些？

1. **版本号机制**：每次修改数据时递增版本号，更新时检查版本号是否一致
2. **CAS**：原子操作，比较内存值与预期值，相同则更新

## CAS是什么？底层原理是什么？

CAS是无锁算法，包含三个操作数：内存位置（V）、预期原值（A）、新值（B）。如果V==A，则将V更新为B。

**底层原理**：
1. 依赖CPU原子指令（如x86的`CMPXCHG`）
2. Java通过`Unsafe`类的`compareAndSwap`方法实现

## 乐观锁有哪些优缺点？

**优点**：
1. 无锁开销，提高并发性能
2. 非阻塞，减少上下文切换
3. 适合读多写少场景

**缺点**：
1. 冲突时重试消耗CPU资源
2. 不适合长事务，增加冲突概率
3. ABA问题：值被修改后再恢复原值无法检测（可用`AtomicStampedReference`解决）

## 什么是ABA问题？如何解决？

**问题**：值从A变为B再变回A，CAS操作误认为值未修改。

**解决方案**：使用`AtomicStampedReference`，每次修改时增加版本号。

## 乐观锁和悲观锁的适用场景是什么？

| 场景 | 乐观锁 | 悲观锁 |
|------|--------|--------|
| 读写比例 | 读多写少 | 写多读少 |
| 冲突频率 | 冲突少 | 冲突多 |
| 典型实现 | CAS、版本号 | `synchronized`、`ReentrantLock` |

## 锁与原子类的区别是什么？

- **锁**：通过阻塞线程保证线程安全，适合保护复杂操作
- **原子类**：基于CAS实现，非阻塞，适合简单原子操作，性能更好

## 什么是锁的饥饿和公平性问题？

- **锁饥饿**：某些线程长期无法获得锁，导致性能下降
- **公平性**：通过公平锁确保所有线程都有机会获得锁，但会有性能开销

## 什么是 Condition 接口？

Condition接口用于替代传统的`wait()`、`notify()`方法，提供更灵活的线程等待和唤醒机制。与Lock配合使用，每个Lock可关联多个Condition对象。

**核心方法**：
- 等待：`await()`、`await(long time, TimeUnit unit)`
- 唤醒：`signal()`、`signalAll()`

## ThreadLocal原理是什么？

ThreadLocal为每个线程提供独立变量副本，实现线程隔离。

1. **存储结构**：每个Thread对象包含`ThreadLocalMap`，键为ThreadLocal实例，值为线程局部变量
2. **工作流程**：`set()`/`get()`操作当前线程的ThreadLocalMap
3. **内存管理**：Entry使用弱引用指向ThreadLocal，避免内存泄漏

**注意**：使用后调用`remove()`清理，防止内存泄漏。

## 两个线程同时操作同一条数据，如何保证数据安全？

* **单实例服务**

    * *使用本地锁即可*（如 `synchronized`、`ReentrantLock`），因为所有线程都在同一 JVM 中。

* **多实例/分布式部署**

    * *必须使用外部锁*，因为本地锁无法跨 JVM：

        * **数据库锁**：行锁、`SELECT … FOR UPDATE`
        * **乐观锁**：版本号
        * **分布式锁**：Redis / Zookeeper

* **核心要点**：
  **是否需要数据库/分布式锁，取决于是否是分布式场景。本地锁只能在单实例生效。**

## 什么是线程的虚假唤醒？为什么使用 while 而不是 if？

**虚假唤醒**指线程在没有收到`notify()`或条件真正满足的情况下，从`wait()`中意外苏醒。Java规范明确允许虚假唤醒。

**为什么用`while`不用`if`**：`if`只检查一次条件，若虚假唤醒会直接执行导致错误。`while`每次苏醒后重新检查条件，确保条件真正满足。

## 为什么在多线程中不建议使用 `static` 共享变量？

1. **线程安全问题**：`static`属于类级别，多线程同时修改可能导致数据竞争、状态错乱
2. **可见性问题**：CPU缓存可能导致不同线程读取到旧值
3. **可维护性下降**：共享状态破坏封装，增加耦合

**替代方案**：`AtomicInteger`、`synchronized`代码块、`ConcurrentHashMap`

## 如何实现无锁的线程安全单例？

1. **枚举单例（推荐）**：JVM保证只加载一次，天生线程安全，防反序列化、防反射

```java
public enum Singleton {
    INSTANCE;
    public void doSomething() { }
}
```

2. **静态内部类单例**：依赖JVM类加载机制保证线程安全，懒加载

```java
public class Singleton {
    private Singleton() {}
    private static class Holder {
        private static final Singleton INSTANCE = new Singleton();
    }
    public static Singleton getInstance() {
        return Holder.INSTANCE;
    }
}
```

3. **饿汉式单例**：类加载时就创建实例，JVM保证线程安全

```java
public class Singleton {
    private static final Singleton INSTANCE = new Singleton();
    private Singleton() {}
    public static Singleton getInstance() { return INSTANCE; }
}
```

## JUC 有了解吗？

JUC是Java并发工具包(java.util.concurrent)，包含：
1. **锁机制**：ReentrantLock、ReadWriteLock、StampedLock
2. **线程池**：ThreadPoolExecutor、ScheduledThreadPoolExecutor
3. **并发容器**：ConcurrentHashMap、CopyOnWriteArrayList、BlockingQueue
4. **原子类**：AtomicInteger、AtomicReference等
5. **同步工具**：CountDownLatch、CyclicBarrier、Semaphore

## 线程池任务提交流程？

1. 线程数 < corePoolSize → **新建线程**
2. 线程数 ≥ corePoolSize → 进**工作队列**
3. 队列满了 + 线程数 < maxPoolSize → 新建非核心线程
4. 队列满了 + 线程数 = maxPoolSize → **拒绝策略**

## 线程池核心参数和任务提交流程？

### 核心参数

| 参数 | 含义 |
|---|---|
| corePoolSize | 核心线程数 |
| maxPoolSize | 最大线程数 |
| keepAliveTime | 非核心线程空闲存活时间 |
| workQueue | 阻塞队列（任务缓冲区） |
| threadFactory | 线程工厂 |
| rejectedExecutionHandler | 拒绝策略 |

### 提交流程

1. 线程数 < corePoolSize → **新建核心线程**
2. 线程数 ≥ corePoolSize → 进**工作队列**
3. 队列满了 + 线程数 < maxPoolSize → 新建非核心线程
4. 队列满了 + 线程数 = maxPoolSize → **拒绝策略**

### 四种拒绝策略

- AbortPolicy — 抛异常（默认）
- CallerRunsPolicy — 退回给调用者线程执行
- DiscardPolicy — 静默丢弃
- DiscardOldestPolicy — 丢弃队列头部旧任务

## 线程池核心参数有哪些？核心线程和最大线程区别？

| 参数 | 作用 |
|------|------|
| corePoolSize | 核心线程，一直存活（即使空闲也不会回收） |
| maxPoolSize | 最大线程数，核心不够 + 队列满了才扩 |
| keepAliveTime | 非核心线程空闲多久后回收 |
| workQueue | 阻塞队列，核心忙时任务先进队列等待 |
| threadFactory | 线程工厂，自定义线程名 |
| rejectedExecutionHandler | 队列满 + 线程数到最大 → 拒绝策略 |

- **核心线程 vs 最大线程**：核心线程不会被回收（除非 `allowCoreThreadTimeOut`），最大线程里的非核心线程空闲超时即销毁。

## synchronized 锁升级过程是怎样的？

- 锁升级链路：**偏向锁 → 轻量级锁 → 重量级锁**（不可逆）
- **偏向锁**（无竞争）：同一线程反复获取，对象头记录线程 ID，CAS 都不需要。另一个线程竞争时撤销偏向。
- **轻量级锁**（竞争不激烈）：CAS 自旋抢锁，适合锁持有时间短。自旋失败次数多 → 膨胀。
- **重量级锁**（竞争激烈）：自旋耗 CPU，膨胀为 OS mutex，线程阻塞进入等待队列，切换成本高。
- 设计思想：大多数锁生命周期内没有竞争，用轻量手段覆盖常见场景，竞争激烈才走内核态。

## ThreadLocal 是什么？有哪些使用场景？内存泄漏是怎么造成的？

**是什么**：线程本地变量，每个线程持有独立副本，线程间隔离。实现：每个线程内部有一个 ThreadLocalMap，key 是 ThreadLocal 对象的**弱引用**，value 是变量值的**强引用**。

**使用场景**：
- 保存当前请求 userId
- Spring 事务管理器存 DB 连接
- SimpleDateFormat 隔离（线程不安全）

**内存泄漏原因**：
- ThreadLocal 对象（key）是弱引用，GC 可回收
- key 被回收后，value 是强引用不会被回收，且**没有 key 再也访问不到这个 value**，成为无法释放的垃圾
- 线程池线程长期存活 → Entry 一直挂在线程的 ThreadLocalMap 里 → 内存泄漏
- **防治**：用完后必须调 **`remove()`**。get()/set() 时会顺带清理个别 key 为 null 的 Entry，但不保证全覆盖
