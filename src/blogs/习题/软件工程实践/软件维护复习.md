# 软件维护复习

> 软件维护是软件生命周期的最后一个阶段，**维护成本通常占总成本的 60%~80%**，是最昂贵的阶段。  
> 本节围绕「过程 → 方法 → 执行」三个层级展开。  
> 参考：[复习题 - 软件维护章节](./复习题.md)

![软件维护知识图谱](./image/复习题/软件维护.png)

## 一、如何进行软件维护（重点 / 难点 / 考点）

> **软件维护**是指在软件交付使用后，为了**修正错误、改进性能或其他属性**，或使软件**适应新的环境**而进行的修改活动。

### 1. 软件维护的四大类型（必背）

| # | 类型 | 占比（典型） | 含义 | 典型场景 |
|---|---|---|---|---|
| 1 | 改正性维护（Corrective） | 20% | 修正**软件中的错误 / 缺陷** | 修 Bug、修复崩溃 |
| 2 | 适应性维护（Adaptive） | 25% | 使软件**适应新的硬件 / 软件环境** | 升级操作系统、迁移数据库 |
| 3 | 完善性维护（Perfective） | 50% | 为**满足用户新需求**而**改进性能 / 功能** | 新功能、性能优化、UI 美化 |
| 4 | 预防性维护（Preventive） | 5% | 为**预防未来问题**而改进软件 | 重构、文档更新、代码优化 |

> **记忆口诀**：「**改适完预**」= 改正性、适应性、完善性、预防性

### 2. 维护活动的基本过程（重点）

```
维护请求 → 维护组织 → 维护申请 → 实施修改 → 回归测试
   ↓
维护记录 → 维护评价 → 配置管理 → 文档更新
```

### 3. 维护的过程（七步）

| 步骤 | 内容 |
|---|---|
| 1. 维护请求 | 用户 / 客户提出维护请求 |
| 2. 维护组织 | 由维护团队接收并分类 |
| 3. 维护申请 | 评估必要性、可行性、工作量 |
| 4. 实施修改 | 修改代码 / 配置 / 文档 |
| 5. 回归测试 | 验证修改并测试相关模块 |
| 6. 修改确认 | 用户 / 客户验收 |
| 7. 文档更新 | 更新用户文档 / 维护记录 |

### 4. 软件维护的特点

- 非生产性活动（不直接产生新价值，但维持系统价值）
- 周期长（贯穿整个生命周期，可能数年）
- 维护人员往往是原开发人员之外的团队（理解成本高）
- 修改容易引入新缺陷（蝴蝶效应）
- 维护成本远高于开发成本（通常 60%~80%）

## 二、软件维护的方法与过程是什么（重点 / 难点 / 考点）

> 软件维护的具体技术包括修改设计、代码修改、软件测试等。

### 1. 软件维护的方法分类

按**维护策略**划分：

| 方法 | 含义 | 优缺点 |
|---|---|---|
| 改正性维护 | 修复缺陷 | ✅ 必要 ❌ 救火式 |
| 完善性维护 | 功能 / 性能改进 | ✅ 增值最大 ❌ 可能蔓延 |
| 适应性维护 | 适应新环境 | ✅ 必须做 ❌ 被动 |
| 预防性维护 | 主动改进 | ✅ 降低未来成本 ❌ 短期投入大 |

按**维护技术**划分：

| 技术 | 含义 |
|---|---|
| 理解现有系统 | 阅读文档、代码考古 |
| 修改设计 / 代码 | 实施变更 |
| 回归测试 | 验证修改不破坏现有功能 |
| 配置管理 | 版本控制、变更追踪 |
| 文档更新 | 同步所有相关文档 |

### 2. 影响软件可维护性的因素（重点）

| 因素 | 说明 |
|---|---|
| 可理解性 | 代码 / 文档是否易读 |
| 可修改性 | 修改的难度和成本 |
| 可移植性 | 迁移到新环境的难易 |
| 可重用性 | 模块 / 组件的可复用程度 |
| 可测试性 | 是否易编写测试 |
| 文档质量 | 文档是否齐全、一致 |

### 3. 提高可维护性的原则

- 模块化：高内聚、低耦合
- 信息隐藏：封装实现细节
- 抽象：合理的类 / 接口设计
- 清晰的命名：变量、函数、类的命名要规范
- 完整文档：设计文档、用户文档、维护手册
- 自动化测试：单元测试覆盖关键逻辑

### 4. 维护成本分解

| 成本项 | 占比 |
|---|---|
| 理解需求 / 代码 | 30%~50% |
| 编写修改代码 | 15%~25% |
| 测试验证 | 20%~30% |
| 文档 / 配置管理 | 10%~15% |

> **结论**：理解代码的成本占比最大 → **可读性 = 钱**

## 三、软件维护的方法有哪些，怎么执行（重点 / 难点 / 考点）

> 软件维护的方法分类与实施步骤。常见的方法有**改正性、适应性、完善性、预防性**四种。

### 1. 维护实施步骤（五步）

```
① 需求理解 → ② 设计与编码 → ③ 实施部署 → ④ 验收测试 → ⑤ 配置归档
```

| 步骤 | 内容 |
|---|---|
| ① 需求理解 | 明确维护的具体目标和范围 |
| ② 设计与编码 | 评估影响范围、设计修改方案、编码实现 |
| ③ 实施部署 | 部署到测试 / 生产环境 |
| ④ 验收测试 | 单元 + 集成 + 系统 + 回归 + 验收 |
| ⑤ 配置归档 | 版本控制、文档更新、变更记录 |

### 2. 维护的具体技术

| 技术 | 说明 |
|---|---|
| 结构化维护 | 分解修改任务、逐步实施 |
| 代码修改 | 包括 bug 修复、功能增强、代码重构 |
| 回归测试 | 验证现有功能未被破坏 |
| 软件测试 | 单元 / 集成 / 系统 / 验收测试 |
| 配置管理 | 基线管理、版本控制、变更追踪 |
| 文档更新 | 用户文档 / 设计文档 / 测试文档同步 |

### 3. 维护的执行流程

```
1. 问题报告
     ↓
2. 分类（需求 / 缺陷 / 改进）
     ↓
3. 影响范围评估（关键：识别受影响模块）
     ↓
4. 制定维护计划（时间、资源、风险）
     ↓
5. 实施修改（含代码、文档、配置）
     ↓
6. 测试（单元 + 集成 + 回归）
     ↓
7. 部署上线
     ↓
8. 用户 / 客户验收
     ↓
9. 文档归档
     ↓
10. 维护记录（经验教训）
```

### 4. 常见维护风险与应对

| 风险 | 应对措施 |
|---|---|
| 修改引发新缺陷 | 回归测试 + 自动化测试 |
| 需求理解错误 | 与用户充分沟通、原型确认 |
| 维护人员不熟悉代码 | 良好的文档 + 代码规范 + 代码评审 |
| 工期不可控 | 评估复杂度、预留缓冲、迭代实施 |
| 文档与代码不同步 | 配置管理强制要求 |

### 5. 维护与开发的关系

| 维度 | 软件开发 | 软件维护 |
|---|---|---|
| 目标 | 从无到有 | 改、适应、改进 |
| 难度 | 难度均匀 | 修改往往较难（受既有代码约束） |
| 人员 | 项目团队 | 通常由维护团队接手 |
| 文档 | 设计阶段编写 | 经常缺失 / 过时 |
| 测试 | 新功能测试 | 主要做回归测试 |
