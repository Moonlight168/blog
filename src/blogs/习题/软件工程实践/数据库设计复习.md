## 一、如何设计数据库

**数据库设计的目标**：将现实世界中的数据需求，转换为数据库的**概念模型 → 逻辑模型 → 物理模型**。

### 数据库设计六阶段

| 阶段 | 输出 | 工具 |
|---|---|---|
| 需求分析 | 数据需求 / 业务需求 | 业务流程图、DFD |
| 概念结构设计 | E-R 图（独立于 DBMS） | ER 图 |
| 逻辑结构设计 | 关系模式（数据表结构） | E-R 转关系模型规则 |
| 物理结构设计 | 存储结构 / 索引 | 索引存取方法 |
| 数据库实施 | 建库、建表、索引 | DDL |
| 数据库运行维护 | 性能监控、备份 | DBA |

### 三大模型对照

| 模型 | 关注点 | 与 DBMS 关系 |
|---|---|---|
| 概念模型 | 反映现实世界 | 独立于 DBMS |
| 逻辑模型 | 数据结构 / 关系 | 特定数据模型（关系 / 网状 / 层次） |
| 物理模型 | 物理存储 / 索引 | 依赖具体 DBMS |

## 二、面向对象分析法与结构化方法在建立数据模型时有何异同

> 这是高频考点：两种方法在数据库建模上的**差异**。

### 相同点

- 目标都是：描述系统的数据需求，建立合理的数据模型
- 都需要识别数据对象及其联系
- 都需要规范化（避免数据冗余与异常）

### 不同点（重点）

| 对比项 | 结构化方法 | 面向对象方法 |
|---|---|---|
| 建模基本单位 | 实体 - 联系（ER 图） | 类（属性 + 操作） |
| 数据与操作 | 数据与处理**分离**（DFD + ER） | 数据与操作**封装**（类） |
| 建模工具 | E-R 图（矩形 / 椭圆 / 菱形） | UML 类图（类 + 关系） |
| 行为建模 | 状态转换图、DFD | 状态图、顺序图 |
| 复用方式 | 模块化 | 继承、多态 |
| 数据一致性 | 由 DBMS 保证（外键 / 触发器） | 由类的不变式保证 |

### 核心差异一句话总结

> **结构化方法**把**数据**和**处理**分开建模（DFD + ER）；  
> **面向对象方法**把**数据**和**操作**封装在同一个**类**里（属性 + 方法）。

## 三、如何建模 ER 图

> ER 图是数据库**概念结构设计**阶段的核心工具，详细图示见 [图怎么画 - ER 图](./图怎么画.md#六er-图entity-relationship-diagram)。

### ER 图三要素

| 要素 | 符号 | 含义 |
|---|---|---|
| 实体（Entity） | 矩形 | 现实世界中可相互区分的事物 |
| 属性（Attribute） | 椭圆 | 实体的特征 / 性质 |
| 联系（Relationship） | 菱形 | 实体之间的关联 |

### 联系的基数（三类，考点）

| 类型 | 含义 | 写法 |
|---|---|---|
| 1 : 1 | 一对一 | `A 1 ──── 1 B` |
| 1 : N | 一对多 | `A 1 ──── N B` |
| M : N | 多对多 | `A M ──── N B` |

### 属性类型

| 类型 | 含义 | 示例 |
|---|---|---|
| 简单属性 | 不可再分 | 学号、姓名 |
| 复合属性 | 可再分为子属性 | 通讯地址（省/市/街道） |
| 单值属性 | 只有一个值 | 身份证号 |
| 多值属性 | 有多个值（**单独建表**） | 电话号码、兴趣爱好 |
| 派生属性 | 由其他属性计算得出 | 年龄（由生日推算） |
| 主键（Key） | 唯一标识一个实体 | 部门编号（下划线标识） |

### ER 图示例

  部门名称

## 四、如何将类图转化为数据库表结构（难点 / 考点）

> 这是面向对象 → 关系数据库的**核心映射问题**。

### 映射总览

| 类图元素 | 映射为 | 说明 |
|---|---|---|
| 类（Class） | 一张**表（Table）** | 表名 = 类名（常用复数） |
| 类的属性 | 表的**列（Column）** | 类型一一对应 |
| 类的方法 | **不映射**（存于应用层） | — |
| 主键 | 表的**主键（PK）** | 唯一标识一行 |
| 1:1 联系 | 在**任一方**加外键 + UNIQUE 约束 | — |
| 1:N 联系 | 在 **N 端**加外键（指向 1 端） | — |
| M:N 联系 | **新建中间表**（含两端外键） | 中间表 PK = 两端 PK 组合 |
| 聚合 / 组合 | 与**关联**映射方式相同 | 组合可加级联删除 |
| 泛化（继承） | 三种策略（见下） | — |
| 依赖 / 实现 | 一般不映射 | — |

### 继承的三种映射策略（难点）

**策略一：单表继承（Single Table）**

> **所有类合并到一张表**，用**辨别列**区分。

```
Person（单表）:
  id (PK)
  type（辨别列: S/T）
  name
  salary  ← Teacher 用
  subject ← Teacher 用
  grade  ← Student 用
```

- ✅ 简单、查询快
- ❌ 字段稀疏（NULL 多）、浪费空间

**策略二：具体表继承（Table Per Concrete Class）**

> **每个具体类一张表**，抽象类不建表。

```
Person（不建表）
Student（表）: id, name, grade
Teacher（表）: id, name, salary, subject
```

- ✅ 无 NULL 字段
- ❌ 公共字段重复、改字段要改多表

**策略三：类表继承（Table Per Class / 垂直切分）**

> **每个类各建一张表**，子类表只存自己的特有字段 + 主键。

```
Person（表）:      id (PK), name
Student（表）:     id (PK, FK→Person), grade
Teacher（表）:     id (PK, FK→Person), salary, subject
```

- ✅ 符合范式、无冗余
- ❌ 多表 JOIN、性能差

### 类图转表结构示例

**类图**：

@startuml 类图转表
title 学生-课程 类图

class Student {
  - studentId: String
  - name: String
  + enroll(course)
}

class Course {
  - courseId: String
  - name: String
  - credits: int
}

Student "1" --> "*" Course : 选课 (M:N)

@enduml

**转换结果（3 张表）**：

```
-- Student 表（实体）
CREATE TABLE Student (
  student_id VARCHAR(20) PRIMARY KEY,
  name       VARCHAR(50)
);

-- Course 表（实体）
CREATE TABLE Course (
  course_id VARCHAR(20) PRIMARY KEY,
  name      VARCHAR(100),
  credits   INT
);

-- 选课表（M:N 联系 → 新建中间表）
CREATE TABLE Enrollment (
  student_id VARCHAR(20),
  course_id  VARCHAR(20),
  enroll_date DATE,
  score       DECIMAL(5,2),
  PRIMARY KEY (student_id, course_id),
  FOREIGN KEY (student_id) REFERENCES Student(student_id),
  FOREIGN KEY (course_id)  REFERENCES Course(course_id)
);
```

**转换步骤总结**：

1. 每个类 → 一张表（含主键）
2. M:N 联系 → 单独建表（含两端 PK + 联系属性 + FK）
3. 1:N 联系 → 在 N 端加 FK
4. 1:1 联系 → 在任一端加 FK + UNIQUE
